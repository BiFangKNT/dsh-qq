## 文件信箱、共享文件和记忆到底有什么区别

| 名称 | 保存什么、谁维护 | 是否自动提供给主模型 |
| --- | --- | --- |
| 文件信箱 `doorDir` | 外部程序或另一个 agent 放入 `.md`；本插件只计未读；模型自行读、写回信；对方自行读取 | 现为历史消息正文中的未读数和最近路径，不直接提供信件正文 |
| 共享文件工具 `qq_memo` | 配置 `memoryRoot` 后，由工具在公共目录读、追加、覆盖 md/txt；不同聊天可共用 | 不自动注入；模型调用工具才读取。不是结构化记忆，也没有事项自动失效规则 |
| 统一记忆 `qq_memory` | 按聊天保存 `memory.json`；工具和独立维护模型更新事项、事实、已确认词义，保留版本与依据 | 当前有效内容放请求末尾状态区；旧状态不进入后续输入和 compact |
| 旧便签、交接、话头、事实卡、群词典 | 升级时一次迁移并留备份；旧事项先待核实。当前正常流程不继续维护这些文件 | 已停止旧的首轮注入，不应重新接回旧机制 |
| 日记文件 | 外部日记脚本及其模型会话维护 | 不会因为写了日记就自动变成当前聊天记忆 |
| 聊天流水与宿主历史 | 前者是插件落盘文本，后者是宿主事件与模型历史；均不是当前事项表 | 宿主历史参与正常对话；流水仅在主动查询或其他明确读取时使用 |

这些能力有不同用途，不能因为名字相似就直接合并，也不能因为没有页面就直接删除。先确认产品是否需要，再决定保留哪些入口。

### 文件信箱已确认的具体边界

- 启用键 `doorDir` 不在页面，也不在 `OVERRIDABLE`；在插件 `settings.json` 填它不会启用功能。页面却显示两个从属配置，用户看不到它们依赖什么。
- 忽略隐藏、草稿和回信前缀文件，按修改时间计算未读；已读写入该目录的 `.已读.json`，同名文件修改后重新未读。
- 所有使用同一目录的会话共用已读状态，没有按群或私聊隔离，也没有验证发件人。`doorSenderLabel` 只是显示文字。
- `outbound.js` 在名为 `read` 的工具**调用时**登记已读，不等读取成功；`markDoorRead` 只匹配文件名，没有核对实际读取路径属于信箱。其他目录同名文件也可能被误认。
- 未读提醒放在用户消息正文，历史里的旧数量会保留；没有使用已实现的临时末尾状态区。这是上游功能与 fork 新状态区尚未统一的位置。
- 它没有收件 API、自动送信、送达确认或独立阅读会话。现有代码不能支持这些额外含义。

依据：`src/door.js`（已移除，见 Git 历史）、[outbound](../src/outbound.js)、[inbound](../src/inbound.js)、[wake](../src/wake.js)。文件名匹配和调用即已读的实现可追到上游 `602b3ae`；fork 增加显示配置并不等于引入了整套信箱。

## 配置为什么难以理解和维护

当前静态统计：schema 有 108 个顶层声明，覆盖名单有 72 个键，页面有 55 个直接字段调用，另有成员称呼、逐群 @ 覆盖、版本确认等手写控件。它们不是同一口径，不能相减得出“缺少多少个功能”。

问题是一个选项至少要在 [config](../src/config.js)、[settings](../src/settings.js)、[client.js](../client.js) 里分别维护，还涉及 bundle 默认值、文档和具体模块。没有一个地方能直接回答它在哪里改、什么时候生效、关闭后停什么。

### 明显缺少入口说明的配置

| 情况 | 配置与影响 |
| --- | --- |
| 默认开启，却没有 QQ 页面入口 | `aiGirls`、`asrEnabled`、`chatLog`、`auditOutbound` 等；功能性质和依赖各不相同 |
| 整组能力只能 profile 配 | `reading*`；`doorDir`；`memoryRoot`；模型路由 `provider/model` 等 |
| 接受文件覆盖，却没有直接页面字段 | `reconnectMs`、`imageCacheDir`、`peerChatMaxTurns`、`showToolResults`、`streamReply`、`streamMaxChunks`、`faceCollectHint`、`faceSendGapMs`、`faceSendMaxPerHour`、`goodnightWords`、`asrEnabled`、`asrPython`、`asrModel` |
| 有页面字段，但影响实际行为的相关项不可见 | 页面改 `splitDelayMs`，默认 `splitDelayMeanMs=500` 却优先走随机间隔；页面改这个固定间隔通常没有效果 |
| 源码使用，却没有 schema 定义 | `bridgeReceipt`、`contextMemoryKeep`；不能照正常设置路径发现它们 |
| 有意只用于迁移 | `ownerLabel`、`groupFree` 等，应与缺失入口分开，不应重新显示成可用开关 |

“只在 profile 配置”本身不一定是缺陷。需要明确哪些是部署参数、哪些应该让用户在页面控制，而不是把全部 108 项塞进页面。

### 已确认的配置行为问题

1. **移除覆盖不恢复基础配置。** API 注释说传 `null` 会回到 profile 值，但 `applyOverrides` 只写现存覆盖键。内存复现：基础 `debug=false`，覆盖成 true，再应用空覆盖，结果仍为 true。旧 `settings-watch` 测试还把保留旧值当预期。核心逻辑已存在于上游 `730b5bb`，不是后续群设置迁移引入。依据：[settings](../src/settings.js)、[settings-watch 测试](../test/settings-watch.test.mjs)。
2. **热更新不是所有模块共同遵守的约定。** `createInbound` 初始化时保存缓存根目录和图片大小上限；日志函数在创建时固定是否输出 debug。配置对象变了，不代表这些值也变了。API 的重启清单未完整反映这些差异。依据：[inbound](../src/inbound.js)、[index](../src/index.js)、[settings](../src/settings.js)。相关机制横跨上游代码与后续修改，整理时逐项归属，不能仅凭当前行作者归因。
3. **页面上的固定分条间隔被默认随机间隔覆盖。** `index.js` 优先使用 `splitDelayMeanMs`，大于零才随机；只有它为零才使用页面里的 `splitDelayMs`。该组合在上游 `05e338c` 已存在。依据：[config](../src/config.js)、[index](../src/index.js)、[client.js](../client.js)。

## 权限、外发和数据不能只靠名称判断

- `ownerIds` 不是全局管理权限闸门；聊天命令不检查它，部分工具各自检查。当前“谁能做什么”没有统一说明。
- `qq_memo` 配置后直接由插件进程读写共享目录，执行函数没有 QQ 会话或 owner 校验；路径检查不等于调用者授权。它与默认逐聊天目录隔离是两个不同边界。
- 原 `qq_group_history` 无 owner 校验，原 `qq_private_history` 单独读取好感文件。现已统一为 `qq_history`：默认仅当前聊天，跨聊天需要授权账号私聊和目标访问许可，查询不再与好感度耦合。
- 普通正文、互动工具、文件、跨目标发送、空间发布分别执行检查；当前阅读静默遗漏已经说明，不能以一个总开关的描述代替逐出口核对。
- 以上先记录事实。哪些应该放开、哪些需要授权，要按用途决定；本轮没有擅自新增限制。

主要依据：[tools](../src/tools.js)、[tools-extra](../src/tools-extra.js)、[message-tools](../src/message-tools.js)、[inbound](../src/inbound.js)。原共享文件与群历史来自上游；原私聊历史、空间发布及现统一查询来自 fork。涉及混合代码时分别说明。

## 补充：旧部署和关闭开关也需要检查

### 工作目录里的 AGENTS.md 是另一份提示词来源

调研时，[workspace.js](../src/workspace.js) 首次创建聊天目录会生成 `AGENTS.md`；已有文件永不覆盖。这个规则来自上游 `c3ea240`，fork 后续改过模板内容，沿用了保护已有文件的做法。项目整理第三批已替换这条生成路径，当前行为见[第三批实施进度](#第三批实施进度)；以下保留问题依据及设计要求。

这意味着修改源码里的模板，不会同步旧目录。`/new` 更换会话，但同一个群或私聊仍使用原工作目录，也不会因此替换该文件。配置参考已有手动检查旧模板的说明，但设置页和升级流程没有将它与 system 同步区别讲清。

已核对官方 `@deepseek-ai/dsh-agent-instructions@0.2.2-rc.2` 发布包及源码：宿主挂载该功能时，工作目录指令作为带 `agent-instructions` 来源的 user 消息进入历史，不属于 `@deepseek-ai/dsh-system-prompt` 管理的固定 system，也不是临时末尾状态区。首次加载时放在本步接纳的用户消息之后、循环追加的状态区之前；以后保留在历史原位置，内容不变不重复追加。变更被发现后追加更新说明，旧指令消息保留并可参与 compact。官方不会持续监听任意外部编辑；相关文件工具操作、恢复会话等会触发核对。[官方说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/context/agent-instructions/README.md)

`dsh-base` 默认启用这项功能，具体预设或部署可以关闭。本轮没有读取真实部署配置，不能仅凭插件生成了文件就断言部署一定加载它。system 锁定不会锁住这类历史消息，因此这条加载路径不适合承载 QQ 插件的固定框架定义。

当前模板本身也还有与真实存储不一致的地方：

- 模板说表情收藏在当前目录的 `./表情包收藏.json`；实际 [faces.js](../src/faces.js) 优先使用 `faceRoot`，其次 `workspaceRoot`、`cwd`。默认不一定在该聊天子目录。
- 页面把工作目录称为“记忆区在这儿”；统一事项与事实实际保存在插件家目录的 `memory/` 下。聊天目录里的日记和项目文件只是另一类资料。
- 模板按生成当时的 `memoryRoot` 决定是否介绍共享文件工具。以后改变配置，旧文件不会自动跟着改。

固定框架定义进入现有锁定 system；停止用工作目录 `AGENTS.md` 承载这部分内容。以下为确定的设计要求，已在项目整理第三批实现：

1. 框架定义只说明消息结构与来源标记、插件入口和工具职责等稳定含义；不保存事项、人物事实、情绪、日记或索引维护要求、用户自定义约定及当前配置值。实际权限和触发条件由程序保证。
2. 定义通过现有 `buildChatPrompt` 和 `@deepseek-ai/dsh-system-prompt` 组装进固定 system，只保留一份正文来源。如提取为独立说明源文件，使用普通文件名，避开 `AGENTS.md`、`CLAUDE.md` 等宿主指令候选名；不同时维护文件正文和代码副本，不要求模型自行读取源文件。
3. 框架定义的实际内容纳入现有 system 变更判定与快照。新建、成功压缩或明确强制同步时使用最新内容，其余时间沿用旧 system；保存后的待同步提示继续提供原有四个选项，不新增另一套同步机制。
4. 停止在 QQ 工作目录生成插件的旧 `AGENTS.md` 模板。迁移只处理可精确确认由插件生成且未被手改的旧文件：先备份到不会被宿主识别为工作目录指令的位置，再停用原文件，避免同一套框架定义又作为 user 消息注入。无法确认归属或有手工改动时保留原文并报告冲突，不能显示为迁移完成。
5. 迁移限定在 QQ 独立工作目录。宿主公共 cwd、仓库根目录、用户全局指令及其他 Agent 的文件不接管，也不全局关闭官方工作目录指令功能。人设等继续使用已有配置入口，不迁入框架定义。

最终顺序为“固定 system（框架定义、聊天规则、人设）→已有历史→本次消息→临时末尾状态区”。框架定义由 system 快照保存，不再依赖聊天历史和 compact 摘要保留；动态状态继续在响应后清理。已进入旧历史的指令不批量改写，停止新的注入不等于旧历史已经清除；升级会话按既有 system 同步规则处理。

宿主仍可能提供用户自己的工作目录指令等辅助消息，它们不算新的 QQ 发言、不推进处理位置、不触发事项或情绪计分，容量检查须包含这些实际输入。与群消息方案的关系见[群消息背景说明](group-message-design.md#3-按真实消息顺序提供背景)。

实现验证包括定义唯一来源、完整 system 锁定与变更提示、旧模板归属与备份、用户文件保护。真实宿主指令加载行为仍需部署验证；最终容量计量继续由群消息第三批负责。调研阶段没有改实际会话目录，新版在运行时首次使用各独立目录时执行迁移。

### 已有夜间积压时关闭作息，消息会滞留

[sleep.js](../src/sleep.js) 的 `tick` 在 `sleepMode=false` 时直接返回，但已有 `pending` 仍保留；`isHolding` 又会让 [SessionManager](../src/session.js) 暂不回收该会话。因此用户关闭作息后，新消息可正常处理，旧积压却不再交付，直到重新开启等条件满足。这里指关闭分类器、没有既有持久队列的普通私聊路径；分类器路径另有持久待交付队列，不能混为一谈。相关作息分支已存在于上游 `472bb15`。

“回收”只指卸载闲置 Agent 和插件内存记录，不删除磁盘上的聊天历史或统一记忆，下次消息到来时再恢复。当前群聊默认闲置 30 分钟回收，私聊默认至少 12 小时；正在处理任务或被 `keeper` 保留的会话跳过回收。作息积压导致的长期保留，本身不持续调用模型，但使资源不能正常释放，积压也没有进展。它与 `/new` 切换模型会话、compact 压缩上下文是三件不同的事。

已用内存假会话复现：先暂存一条夜间消息，再关闭作息，模拟上午 tick，交付任务为 0、会话仍被保留；重新开启后模拟同一时间 tick，才安排交付。未请求模型或连接 QQ。

这里要补的是开关的完整行为：关闭后不再拦截新消息，已有暂存内容恢复到正常交付队列，保留原时间并只交付一次。不能把“关闭功能”实现成“停止处理留下的数据”。这是拟定的修复行为，尚未实现；夜间积压的持久化、容量和附件处理仍需与群消息第三批一起核对。

### 续查发现：暂存、额度和任务结束没有统一处理

| 遗漏 | 影响与证据 | 来源和后续要求 |
| --- | --- | --- |
| 普通私聊的旧夜间暂存只在内存里，按模型 session ID 保存 | [inbound](../src/inbound.js) 未启用分类器且没有旧持久队列时走普通入口；[sleep](../src/sleep.js) 只保存最多 500 字文本，不携带准备好的完整正文和附件。模块重启清空；切换 session 后新 ID 查不到原积压。聊天流水即使有原文，也没有自动恢复交付进度 | 内存暂存和截断来自上游 `472bb15`；与 fork 新建会话、持久队列的接合需一起处理。已用假会话复现 ID 切换后积压留在旧 ID、模块重建后无待交付项。应纳入统一消息保存与容量处理，不能再加另一套临时队列 |

| 阅读等待超时并不代表模型停止 | `src/reading.js`（已移除，见 Git 历史） 用 `Promise.race` 停止等待，随后将 `quietRound` 设为 false，没有终止该模型轮次。已用假模型和缩短的测试计时复现：模型尚未结束，静默标记已经撤销；晚到的正文存在外发路径 | 来自上游 `822f36b`。必须按真实任务结束或确认取消后解除该轮限制；不能只补各发送工具的 `assertQuiet`，也不能粗暴取消同一 Agent 上的其他正常任务 |
| 会话映射文件损坏时自动回到初始代数 | [session-state](../src/session-state.js) 读取失败后回到第 0 代，[session](../src/session.js) 据此重新计算 session ID；已有初代历史时存在重新选中 `/new` 以前会话的路径。旧测试直接把归零当成正确行为 | 来源为上游 `602b3ae`。保留损坏文件并明确报错，不以“新建默认状态”掩盖恢复失败；切换记录需可靠落盘。此项依据代码和现有测试确认，未在真实宿主制造损坏 |

这些问题共同说明：消息、配置、模板和运行状态要分别定义在重启、新建会话、关闭开关、超时和读取失败后的行为。不是每项都需要新模块，但不能只验证第一次启动的正常路径。

## 拟定的整理方案

以下是后续实现安排，不是当前功能已经改变。调研记录了现有功能，不表示这些功能都应保留；也不能把“统一整理”理解为给所有旧功能补入口、补测试。第一批只修基础配置和现有说明，不决定可选功能的去留。

### 先决定可选功能的去留

第二批先收束用途，再决定实现范围。只有确定保留的功能才修复和补入口；确定移除的功能清理入口、调度、提示词和相关配置，并说明旧数据如何保留或迁移。不为准备移除的功能先完善一遍，也不擅自删除用户文件。

| 功能 | 当前决定 |
| --- | --- |
| 定时阅读 | 已移除阅读调度、书签相关设置、提示词及专用代码，不再完善入口或修补专用额度；已有用户文件保留 |
| 文件信箱 | 已移除未读提醒、读信登记、回信设置及专用代码；已有信件和回信文件保留 |
| 共享文件工具 `qq_memo` | 后续整体改造成与聊天 Workspace 统合的可选资料检索（RAG），聊天私有资料保持隔离，另支持管理员启用的公共资料；两者使用同一套检索。当前代码保留作过渡，已有用户文件保留；第二批已完成的权限修复仍有效 |
| 群词候选定时扫描 | 已移除，不影响正常记忆维护与 `qq_memory` 工具；已有候选和用户文件不随代码清理删除 |
| AI 拟人同人角色资料 | 保留参考用途，停止整份加入 system，改为可选资料、按需检索；检索入口尚未实现 |
| 查梗 | 保留查资料的用途，取消要求用户提供特定 SQLite 数据库的方式；与角色资料共用资料入口，由程序建立索引，不再各做一套导入与检索 |
| 主动发言 | 已确认保留为可选功能，默认关闭；需要时明确开启，并说明会额外调用主模型 |
| 睡前提醒和休息时段处理 | 已确认两项都保留为可选功能；分别说明提醒的模型成本、休息时段的私聊暂存及群聊暂停行为，不把其中一项的设置误作另一项的总开关 |

上述去留不明确时先确认，不进入对应功能开发。可以独立推进已明确需要的基础功能，不能把未经确认的可选功能完善工作当作群消息第三批的前置条件。

群词候选扫描的实际规则：从机器人已发回复中匹配“什么意思”“没懂”等固定字样，取此前最近一条群友消息，去掉 @ 后至少 4 个字符便把整句话写为候选。不做语义判断、不提取具体词义，反问及多人交错发言都可能误命中或错配。扫描本身不调用模型；不能将它描述为已理解或学会词义。当前生产入口写统一记忆候选，旧源码中写 `群词典.md` 的注释不代表当前路径。

### 资料入口与共享文件

当前没有通用资料检索实现。`qq_memo` 提供 `list/read/append/write`，是可选共享文件工具，不会建立检索索引；`qq_meme` 只查询特定表结构的现成 SQLite 文件；角色资料当前仍整份进入 system。不能把这些现状称为已落地的 RAG。

2026-11-13 更新：用户明确原共享目录承担的记忆职责已由统一记忆系统接管，后续将其整体改造成可选资料检索（RAG），与聊天 Workspace 统合设计，支持聊天私有资料和可选公共资料。这取代此前“独立保留共享文件工具，再并列新增资料入口”的安排，公共资料不再承担共享记忆或通用写文件职责，不扩充公共日记或共享事项。

用户提供资料，程序负责建立和更新检索索引，模型按需搜索并取得相关片段和来源；角色知识和梗知识共用这条路径。索引属于可重建的内部数据，不能要求用户自行制作数据库。正文不整份加入 system，不宣称检索命中就等于资料正确。旧 `memeDb` 若需要迁移，由程序提供明确的导入路径，不把旧数据库结构继续暴露为普通用户的配置要求。

先采用本地标题、别名、关键词检索，不增加向量模型调用或独立检索服务。首版已确认仅支持本地文件、目录和可选资料包，不支持网页网址导入。具体格式、更新方式和检索容量在来源范围确认后设计，不在本次讨论中假定已经实现。

职责收束为：Workspace 管理当前聊天的文件，RAG 为其中明确选入的参考资料及管理员启用的公共资料提供检索；统一记忆维护聊天中的事项与事实。RAG 使用同一套导入和检索机制，按可见范围区分聊天资料与公共资料，不复制原文、不另建共享记忆系统。

聊天私有资料按机器人身份 + 私聊/群 + 对方/群号隔离，公共资料由管理员导入并为获准聊天启用。一次查询只能访问“当前聊天明确选入的资料 + 为它启用的公共资料”，不能访问其他聊天资料。公共范围先限当前机器人，不自动扩到整个 DSH 的其他 Agent。新建 session、compact 和重启不清空资料；共用 cwd 也不自动共享私有资料。

只索引明确选入的文件、目录和资料包，不递归扫描整个 Workspace，不自动索引聊天记录或统一记忆。聊天记忆中的少量事实和词义继续由现有记忆系统维护，不复制到资料库。原文只维护一份，索引可重建；文件更新或移除后应更新索引，不能继续返回已失效的旧片段。

公共资料对聊天模型只读，不允许聊天记忆自动写入公共库。QQ 侧的资料导入、更新和移除仍仅限授权账号私聊；管理时明确选择目标聊天或公共范围。检索工具只提供查询，不额外扩大 Workspace 文件工具的权限。

旧共享目录保留原文件，迁移时由管理员选择哪些作为公共资料、哪些归入指定聊天；不默认索引整个旧目录，不把私聊内容自动公开。

届时统一调整设置、工具和文案，不再使用 `memoryRoot` / `qq_memo` 表示新功能；旧配置和工具在替代上线时提供迁移说明及必要兼容，不先改名扩出一套长期保留的共享文件接口。新检索结果只在实际查询后提供给模型，不放入固定 system 或每轮末尾状态区；保留查询来源，按正常工具结果处理。

第二批先按已确认决定清理旧功能、修保留功能；资料入口作为单独的实现项明确范围，不借整理入口扩成大型 RAG 平台，也不作为群消息第三批的前置条件。角色资料从旧 system 移出时遵守已有 system 同步规则，不悄悄改写已锁定的会话前缀。

### 功能按用途归位

| 范围 | 收入的功能 | 整理后的要求 |
| --- | --- | --- |
| 聊天基础 | 连接、访问控制、收发、会话、工具预设、群触发、命令、审批与问答、必要的发送限制 | 普通聊天的行为在一处说明，不借其他功能的开关解释 |
| 当前事项与记忆 | 统一记忆及自动维护、查询和更正 | 明确独立模型成本和实际存储路径；继续使用当前末尾状态区，不恢复旧便签 |
| 可选自动行为 | 分类器、主动发言、睡前提醒与夜间处理、定时阅读、群词候选扫描 | 用户能发现是否开启、何时运行、会不会请求模型；逐项定义关闭后的收尾 |
| 文件与资料 | 信箱、共享文件工具、聊天流水、图片和表情收藏、梗库、同人角色资料 | 区分当前聊天、共享目录和静态资料；不统称“记忆” |
| 外部部署工具 | 启停脚本、看门狗、备份、日记脚本 | 在部署文档说明安装与触发，不做成看似由插件控制的假开关 |

上表用于盘点现状，不是新版保留清单。阅读、信箱已确认移除，共享文件工具后续整体改为可选资料检索；其余按前述去留决定处理。只为保留功能补必要入口和依赖说明，不扩展成新的协作平台。基础互动工具不逐个新增开关，特殊依赖或额外后台行为才单独配置。

### 设置页按六组组织

继续使用现有设置页和简单表单，不增加一套配置应用。各项只出现一次，相关设置放在一起：

1. **连接**：协议地址、凭证、账号、连接状态和重连。
2. **访问与消息**：私聊/群访问名单、必须 @ 和逐群覆盖、分类器、合并等待、触发词、沉默、其他机器人、发送节奏。
3. **会话与角色**：预设、工作目录、人设、成员称呼、system 同步；授权名单明确标为工具授权，不与称呼混排。
4. **记忆与文件**：统一记忆维护、聊天流水、媒体依赖与缓存、表情收藏、可选共享文件工具；不再提供文件信箱，其他静态资料按去留决定处理。
5. **自动行为**：只展示确认保留的主动发言、作息等功能，显示启用条件和模型调用说明；不预留阅读等未确认功能的入口。
6. **高级与诊断**：设置服务、模型覆盖、超时与回收、日志、宿主兼容信息；部署专用项说明去哪里配，不强行全部搬到页面。

对于确认保留的可选功能，先显示总开关或必需配置，再显示从属项。例如共享文件工具先提供共享目录入口，并明确留空不启用。关闭时保留配置值，显示为未启用，不让用户误以为从属项能独立启动功能。依赖缺失时显示具体缺项，不能只写“未就绪”。

记忆维护页面直接说明“会另发模型请求”。保留的自动行为应如实说明模型成本和计数含义，例如主动发言的成功次数不等于模型请求次数。只展示用户决策需要的信息，不把内部调度日志堆到页面。

### 配置先统一含义，再减少重复维护

| 改动类型 | 页面应说明的生效方式 |
| --- | --- |
| 访问控制、触发条件、发送限制等运行设置 | 保存后作用于之后的对应处理；不追改已提交请求 |
| 人设、私聊/群聊固定补充等 system 内容 | 保存后标记待同步，沿用新会话、压缩、强制同步、稍后同步四个选择 |
| Agent 预设等会话身份 | 新会话生效；已有会话保留记录的预设，不借“强制同步 system”偷换预设 |
| 连接地址和凭证 | 明确重连后生效，与重启宿主区分 |
| 进程初始化时固定的目录、服务等 | 准确提示重启；有意改为热更新的项目必须同时改实现和验证，不能只改提示 |

保留宿主传入的基础配置，与插件文件覆盖分开；删除覆盖应重新计算基础值加剩余覆盖，不能继续在同一个对象上累积旧值。文件热加载和页面保存共用这套计算及校验规则。

字段的名称、说明、默认值、是否接受文件覆盖和生效方式需要同处维护；页面保留手写布局与特殊控件，不再自行重写另一套含义。先整理实际有入口的字段，再为确认保留的可选功能补必要入口；不先建设通用配置框架。开发文档解释结构，配置参考解释使用方式，两者不重复铺设内部实现细节。

### 提示词按来源整理

| 来源 | 放什么 | 更新方式 |
| --- | --- | --- |
| 固定 system | 框架固定定义、QQ 行为规则、固定角色设定、私聊/群聊的稳定要求 | 从唯一正文来源组装，沿用已落地的锁定、快照和四种同步选项 |
| 请求末尾状态区 | 当前身份和称呼、有效事项与记忆、当前表情资料、本轮是否可沉默 | 每次请求按现值提供，旧状态不进入后续输入和 compact；移除信箱提醒 |
| 单次处理消息 | 本次真实消息，或确认保留的自动行为产生且有明确内部来源的请求 | 说明这次做什么；不是新的用户要求，不伪装成用户证据；不再产生阅读请求 |
| 工具描述 | 工具用途、输入、真实限制、成功和失败的含义 | 按工具实际实现维护，不能宣称程序未执行的权限或确认保证 |
| 插件曾生成的工作目录 AGENTS.md | 仅作为旧模板迁移对象；新版不再用它提供框架定义 | 确认归属后备份并停用，未知手工内容保留并报告冲突；不改宿主或用户的其他指令文件 |

调研时阅读请求标为 `source.kind=user`，主动发言和作息请求标为 `plugin`；而统一记忆按真实用户来源筛选依据。第二批已移除阅读请求；保留的自动行为继续使用明确的内部来源，第三批提示词也注明这是插件内部请求。旧历史不批量改写，不能把旧阅读消息误作为新的用户证据。

提示词只描述确认保留的功能，使用“定时主动发言”等直接名称。功能移除时同步移除相关提示词，不为旧功能单独做改名和完善。保留功能先修实际触发、关闭、外发约束，再让提示词如实描述它们。
