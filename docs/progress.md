### 第一批：context 与 prompt（已完成）

保留现有主请求结构：锁定的 system → 当前 session 的有效历史（包括 compact 摘要和工具结果）→ 本步新输入 → 最新末尾状态区。工具续调时，没有新的聊天输入，状态区放在完整工具调用与结果之后。工具定义单独由宿主提供，不把使用手册再复制进聊天正文。

system 保留宿主与预设提供的稳定规则、插件消息含义和必要行为边界、人设与自定义补充；只在新建、成功 compact 后或用户明确强制同步时更新。当前账号、称呼、事项、记忆、表情状态仍从末尾提供。重试复用本步快照，下一步骤读取最新状态；不修改宿主源码或维护另一套 loop。

检查对象包括宿主与预设贡献后的完整请求，不只检查插件自己的文本；用户自定义人设或其他第三方插件可以另加规则，不能保证任意组合都无冲突。发现这类冲突时说明来源，不静默修改用户内容。插件内置规则的更新也遵守已有 system 锁定与同步流程，不为本次整理强制改写运行中的会话。

| 整理项 | 原问题与依据 | 当前行为 |
| --- | --- | --- |
| 同义规则分散重复 | [prompts](../src/prompts.js) 与 [memory](../src/memory.js)、[identity](../src/identity.js) 的动态输出曾重复解释权限、记忆和来源含义 | 固定解释收束到 system，工具用法收束到工具定义；状态区分为「当前资料」和「本轮条件」，只提供当前值、必要状态及本轮约定 |

| 入站消息夹带长期行为指令 | [inbound](../src/inbound.js) 曾在引用、图片、商城表情正文加入固定说明，关闭表情后仍推荐发送工具 | 新转录只保存消息与来源、引用和附件处理事实；稳定用法放 system 或工具描述，开关和本轮条件放末尾。商城表情 ID 自动登记保留，旧聊天不改写 |

状态区是程序提供的当前资料与明确的本轮条件，不是用户刚说的话。固定 system 说明如何读取这些字段，资料正文不能自行授予权限或改变规则。不能一边笼统写“状态区不含指令”，一边又让它隐含承担沉默条件、收藏策略等控制；这两类内容须明确区分，但沿用同一个末尾区域。

第三批已移除 [outbound](../src/outbound.js) 中仅凭语种、口吻或常见词推断“这是思考”的删改。保留 reasoning 与 text 的结构区分、明确沉默标记、敏感内容检查和必要发送去重；不再为每个误伤句增加白名单。

第四批已限制末尾内容规模：保持聊天隔离及稳定顺序，在共享 token 计算基础上选择完整有效条目；超出部分明确标记未提供及查询入口。具体预算见[记忆设计](memory-design.md#读取方式统一末尾状态区)，不增加向量库或额外检索模型。

### 第二批：访问与隔离（已完成）

宿主入口使用官方 `webServer.getOrigin()` 核对目标和来源，写操作只收 JSON，沿用宿主管理页面的访问边界；独立端口另用本地持久管理密钥，页面明确选择目标端口和密钥，不自动回退。设置接口不回显 NapCat token。升级连接方式见[配置说明](configuration.md#连接)。

取图、表态和撤回共用消息归属检查，撤回须确认当前机器人发送。独立目录初始化失败停止挂载。群审批须由当前授权账号协议 @ 后明确答复；私聊审批仅接管授权对方，其余交回宿主 provider。群问答绑定本轮最后发言人，私聊绑定当前对方；等待期间的身份、权限、取消和并发检查不交给模型处理。

本地覆盖范围和真实部署验收要求见[测试清单](../TESTING.md)，未连接真实 QQ 或模型；真实部署仍需核对宿主入口地址及 OneBot 消息归属回执。

### 第三批：发送与连接（已完成）

普通正文和发送工具使用同一消息 ID 确认规则，负数和零值有效。缺少有效 ID、超时或断线均为未确认，不写已发送记忆、成功额度或默认撤回目标；协议拒绝与调用前未连接分别保留拒绝、未发送状态。正文分段失败或限流后，尚未调用的剩余计划记为未发送，不再悬留为排队中。

工具调用事件不再屏蔽整轮正文。仅针对本轮当前聊天中工具已发送或结果未确认的相同内容去重，允许不同的后续说明；明确拒绝、未发送以及跨聊天发送不抑制当前正文。上一轮或旧会话的迟到回执不影响新轮。通道提示保留真实发送状态，不把“未确认”说成“对方没收到”。

重复启动不新建并行连接，停止会取消重连并结束等待请求；连接回调只作用于其所属连接，旧连接的迟到消息、错误和关闭事件不干扰新连接。手动启动会取消尚未执行的自动重连。

正常 text 不按语言、行首词、口吻或相似句删除。结构化 reasoning 和工具调用消息不外发，明确 `[SILENT]`、敏感检查与必要去重保留。私聊流式仍可能在落定消息前已经发出前半段，无法因后来的沉默标记或工具调用撤回；需整条判断时关闭 `streamReply`。本地覆盖与部署验收见[测试清单](../TESTING.md)。

### 第四批：记忆与输入容量（已完成）

记忆维护按模型容量分批读取新增依据和当前条目（含终态），不携带全部旧版本；单条过长时读取连续片段，成功变更与位置一起原子保存。失败保留当前批，重启核对来源指纹后续接，不跳过旧任务。新增候选核对完已有条目后才保存，不能用条目片段覆盖全文。每批结束让出串行队列，下一轮聊天最多等待当前一批；未整理完的事项明确标为尚未核实，不继续当作最新未完成任务。

末尾状态区使用共享 tokenizer，最多 8192 token 且不超过可用输入硬上限的八分之一。先保留必要条件与缺失说明，再按稳定顺序选择完整条目；遗漏不修改原存储，可经原工具按权限查询。原生宿主验证仍位于完整输入末尾，工具续调刷新，旧状态不进入后续历史或 compact。详细预算和边界见[记忆设计](memory-design.md)。

HTTP 下载按实际读取字节及时取消，Content-Length 仅用于提前拒绝；base64 在解码前检查容量。图片、文件、语音沿用各自限额，写入失败清除半文件，本地语音也在 ASR 前检查大小。覆盖与真实部署限制见[测试清单](../TESTING.md)。本批未实测真实模型维护质量、网络延迟、计费及大型部署档案的调用成本。

## 附件接收与缓存整理（待实施）

本项在当前第四批审查后独立实施，不并入本批代码；完成后再进入情绪与关系。

已核对的现状：图片下载会把 HTTP 响应或 base64 解码成二进制文件再落盘，语音 base64 分支也保存解码后的字节，本地附件缓存本身并不是 base64 文本。待改的是接收来源优先级、协议回执中的大块内容，以及缓存压缩与读取方式；不能把“改为二进制”重复当作一个尚未实现的功能。

- **接收优先 URL**：图片、文件和语音统一优先使用可下载 URL，不因回执同时含有本地路径或 base64 就先读后两者。核对实际 NapCat 接口是否能只返回引用，尽量避免大块 base64 先进入 WebSocket 回执；仅在回执中改选 URL，并不能消除已经收到的 base64 开销。仅返回其他形式时的兼容范围在实施时根据实际接口确定，不默认连续尝试多个来源。
- **缓存使用二进制与无损压缩**：缓存保存附件字节，不把 base64 写入缓存或持久消息正文。压缩按实际收益采用；已压缩的图片、音频或压缩包若再次压缩没有收益，保留原字节。不默认转码、降低图片质量或改变用户文件内容。
- **需要时提供原格式文件**：`read_image`、ASR 及发送工具仍需可用的实际文件路径。压缩只影响存储，读取时按需还原，复用临时文件并纳入清理；解压后也遵守原有大小限制。
- **收束到原缓存链路**：保持聊天与权限边界、实时图片屏蔽、分类图片处理、历史取图例外和待处理附件保护。旧缓存继续可读，不额外维护一套独立附件目录或后台服务。
- **实施前与验收**：使用用户实例实际版本的 NapCat 回执或相应 mock 样例核对 URL、路径、base64 的返回条件，覆盖跨机器部署、链接失效、超限与下载中断、压缩往返字节一致性、重复读取及重启清理。目前未实测 NapCat 是否能按请求避免返回 base64；文档不可访问不阻塞本次计划登记，也不要求迁移或更新用户保留的镜像。
