## 代码怎样安排

沿用现有插件、主会话、作息和主动消息入口，不增加独立服务。

| 部分 | 负责什么 | 实现安排 |
| --- | --- | --- |
| 消息判断 | 是否在和机器人说话；保留暂时不回复的消息 | 独立调用模型、独立保存记录，已接入 |
| 情绪与关系 | 根据经历和时间计算六情、六欲、好感，保存变化原因 | 新增少量内部模块；程序计算数值，模型只识别经历 |
| 作息与主动行为 | 睡眠、唤醒、逐人求助、日常开口、心愿与不满记录 | 扩展现有 `sleep.js`、`wake.js`，由同一份状态决定行为 |
| 表达与查看 | 回复前提供当前说话要求；页面和对话查询 | 每次请求末尾提供一份当前状态，动态更新、不保留旧快照；按权限提供原因 |

同一机器人共用心情，按联系人分别记录关系。跨聊天只传当前表达要求，不传其他聊天的人物、原话、时间和事件原因。动态好感另存，不覆盖现有用于历史访问判断的 `affinity.json`，也不增加管理权限。

情绪计算先按时间推进，再处理一次经历；重复消息不重复计分。锁定、求助和睡眠都有明确的进入、退出条件；关闭某个机制时停止它的后续作用，不补算关闭期间的惩罚。缺失参数采用原文初值或在对应功能开发时确定，并记录在参数文件中。

## 已完成：system 的同步规则

固定人设和聊天规则迁到主会话的 system，每次请求携带同一份内容，不再写入聊天历史。每个 session 保存自己的 system 快照，默认只在新建 session 或成功压缩后按最新配置生成；其余时间锁定。用户也可在设置页明确选择强制同步。恢复旧 session、插件重启、设置热更新和同一轮的工具调用都不单独触发同步。

压缩成功后，在下一次主模型请求前同步；宿主在同一轮内自动压缩也遵循这个规则。压缩失败继续使用旧快照。快照随会话保存，不能因进程重启而悄悄改用新配置。此安排减少 system 变化造成的缓存失效，不保证模型服务一定命中缓存。

设置里修改会影响 system 的配置时，保存新配置，并提示“已保存，现有会话仍使用原提示词”，提供四个选项：

| 选项 | 行为 |
| --- | --- |
| 创建新会话 | 对选中的受影响聊天创建新 session，使用最新 system；旧历史保留在原 session，不作为新会话的完整上下文 |
| 压缩会话 | 对选中的受影响会话执行宿主压缩；成功后保留压缩后的上下文并同步最新 system |
| 强制同步 | 保留当前 session 和完整历史，直接同步最新 system 后重新锁定；不等待压缩，可能降低提示缓存命中率、增加费用和延迟，按钮 tooltip 说明此影响 |
| 稍后同步 | 现有会话继续使用原 system；下次新建 session 或成功压缩时自动使用最新配置 |

操作前展示受影响的聊天，明确新建会话会切换上下文。正在回复的会话等本轮结束后执行新建、手动压缩或强制同步，不中断回复。失败要显示具体会话和原因，未成功的会话保留原快照，仍可稍后同步。重新打开设置页仍能看到哪些会话尚未同步；保存相同内容不重复提示。连接、限流等不影响 system 的设置沿用原生效规则，不要求同步提示词。

动态情绪、对当前发言人的好感及当前场景要求不进入锁定的 system。每次主模型请求时，在全部输入与工具结果之后提供一份简短的当前状态，下一次动态替换；不把旧状态快照追加到聊天历史或交给 compact。只提供当前聊天需要的数值与要求，不列全量关系、采样时间及其他聊天的原因、人物和原话。换人、情绪恢复和特殊状态结束直接反映在当前状态中，不追加历史更正。不因为再次请求就重新计算经历或额外调用模型。接受从上一轮状态位置起的尾部缓存失效，其中包含该状态后生成的回复；更前面的长历史保持相同前缀。具体顺序与验收见[统一末尾状态区](memory-design.md#读取方式统一末尾状态区)。

当前事项与有效记忆按请求读取最新存储；旧便签首轮注入和交付标记已移除。完成、取消和到期不依赖主聊天模型主动改文件。分类器只读完整主上下文和当前状态区，不触发维护或 system 同步。

固定提示词已迁移到宿主正式的 system 组装接口，手动压缩使用 `ctx.compaction.compactNow()`，不修改 `agent/request`。动态情绪尚未实现；有效事实、群词、授权群近况和表情包资料统一通过临时末尾区提供。`personaInSystem=true` 继续表示人设由宿主提供，插件不会重复加入 persona。

授权与称呼独立：`ownerIds` 仅作为相关功能的授权名单，`memberLabels` 按 QQ 号设置称呼。当前配置在末尾状态区提供，下一模型步骤生效；不改变 system、不重写历史，也不改变消息顺序。旧 `ownerLabel` 在运行 QQ 的进程首次启动时持久迁移到当时已有账号，新增账号不继承旧称呼；设置进程不代替其他 profile 提前迁移。内置提示词去掉固定私人性格、事故案例和称呼带来的优先响应要求，具体角色由人设提供。详见[人设与称呼](persona.md)。

完整 system 的锁定保持原有同步规则。插件使用官方 `prompt.context()`，每个模型步骤捕获一次状态，重试复用，工具续调刷新。响应提交后以已记录的空节点替换清理快照；后续模型输入及 compact 不包含旧状态，原快照仍留在日志。未修改的 0.2.2-rc.2 循环已验证，实际部署请求尚未抓取。compact、明确强制同步、模型或工具集变动仍是允许的缓存变化。

快照保存在插件家目录的 `system-prompts/`；同步操作及结果保存在 `prompt-sync/`。设置页与 QQ 分开运行时，设置进程投递操作，由持有该机器人会话的运行进程执行。运行进程离线时显示等待；中途重启的操作显示失败，不自动重放可能已经执行的新建或压缩。压缩没有可处理的历史时也会显示原因，不谎报已同步。

升级已有会话时先保留宿主已记录的 system；原先写入用户历史的规则不主动改写历史，下次新建或成功压缩后使用新安排。安装要求 `@deepseek-ai/dsh-system-prompt >=0.2.2-rc.2`，已验证版本为 rc.2；其他版本需明确接受风险，不能绕过必要接口检查。QQ 会话使用一个完整 system section 锁定最终文本，不能与同一作用域内其他 `complete: true` 的完整提示词并用；有此冲突时宿主明确报错。

## 已完成：框架定义与旧工作目录模板整理

插件框架的固定定义纳入上述 system 组装、快照和同步流程；按唯一正文来源维护，不再通过工作目录 `AGENTS.md` 追加到用户历史。定义说明消息结构、来源、入口和工具职责，不记录记忆、当前状态或用户自定义约定。动态资料继续使用临时末尾状态区。

项目整理第三批已停止生成插件旧 `AGENTS.md` 和日记索引；以完整模板指纹确认归属，匹配后先原样备份到插件数据目录的 `workspace-migrations/*.bak` 再停用。无法确认、有手改、路径链接或备份失败时保留并记录冲突。已有历史不批量改写，不接管宿主公共目录、仓库根目录、全局指令或其他会话文件。框架正文统一在 `src/prompts.js`，通过现有 system 规则摘要判断待同步，不增加同步机制。升级说明见[配置参考](configuration.md#工作目录指令与升级)。

## 已完成：可选的消息判断

本节描述当前实现。群聊“必须 @”已成为硬限制，分类器不能绕过；群聊等待和配置迁移见[第二批实现](group-message-design.md#2-群聊什么时候处理消息)。超大积压处理仍待第三批。

- 默认关闭；群聊与私聊共用一个开关。开启后判断是否在对机器人说话；群聊要求 @ 时，须自身 @ 且判断为 yes 才触发主模型。
- 仍遵循群/私聊访问控制、同类机器人开关、连聊上限、作息与安静轮。审批和问答回复走原控制通道，不等待分类模型。
- 每个机器人身份、每个群/私聊单独保存判断记录，并使用独立的模型 session ID 和判断提示词，不挂载主会话工具。主会话的提示、工具说明及聊天内容仅作为判断背景，不作为分类器指令。
- 判断输入只读主 session 当前完整有效的聊天内容，以及已记录的请求头（系统提示和工具说明）；使用 DSH 的 `deriveMessages()`，压缩后直接读取当前摘要和保留内容，不读取被替换的旧历史。另附全部尚未进入主 loop 的已准备消息、群背景，以及当前消息的发言人、文字、提及、引用、已有语音转写和附件类型，不再使用最近 20/10 条的截取。
- 分类为 `no` 或暂存时，不修改主会话 system、交接内容和历史，也不触发主会话换代。分类器读取已锁定的 system 快照；一次性交接只有正式投递被接纳后才记录完成。审批快速通道同样遵循同类机器人开关。
- `no` 保留消息；`yes` 在当前 @、权限、作息等条件满足时，把截至该消息尚未交付的正文按顺序一起交给主模型。超过 30 条也不静默截断；主会话图片、文件仍走原媒体处理及屏蔽规则。
- 分类器支持实际图片输入：主会话已有图片、待交付图片和当前图片按来源附带，使用宿主 `attachments` 保存的图片引用，不把 URL 或路径当成看图。分类器不受成员图片屏蔽限制；被屏蔽图片不写入主会话缓存，也不将仅供分类的图片引用带入主会话。需要支持图片的分类模型；下载、入库或能力检查失败明确记录错误并保留消息，不偷偷改成纯文本判断。单条沿用前 4 张和 `imageMaxMB` 限制，格式及总大小还受宿主附件服务限制。
- 先严格解析 `yes/no`，失败再从回答正文正则提取独立的 `yes` 或 `no`；两者同时出现视为无法识别。不从推理内容提取。仍无法识别时额外请求两次，三次均无法识别则按 `yes` 放行；不自动换模型。超时、网络及配置错误仍记录失败并保留消息，关闭或卸载不触发兜底。
- 沿用按天落盘的插件日志：重试记录 `warn`，正则成功记录 `info`，最后的兜底明确记录 `warn` 和 `fallback_yes`，包含分类 session、会话、源消息 ID、provider、model、请求次数和原因，不记录分类回答原文或推理。消息记录也保存实际解析方式和请求次数。
- 主模型忙碌时继续分类，正文先保存；空闲后再交付。私聊仍按 `mergeWindowMs` 等待合并，恢复检查约每秒一次。
- 睡眠或回复间隔阻止交付时，待处理消息留在本地；醒来、间隔结束或插件重启后恢复已放行的消息。新收到的后续 `no` 不会被之前的 `yes` 顺带放行。
- 关闭后不再发起分类请求：群聊按当前触发设置处理；私聊未交付消息按顺序转入普通处理，新消息不越过旧队列。不同账号不能恢复彼此的记录。

实现入口为 `src/address-classifier.js` 与 `src/inbound.js`；设置页、配置定义和覆盖白名单已接通。

### 保存与边界

消息进入队列前先保存源事件，完成媒体处理后保存正文，再保存判断结果。等待上一条判断时收到的新消息也已落盘；重启后可继续准备。普通群消息等待与分类器共用这份待交付记录，不重新判断旧背景；记录兼容已有格式，仍位于插件家目录的 `address-classifier/`。关闭分类器后，群消息按当前触发设置继续交付，私聊旧队列按顺序转入普通处理，无新消息也会恢复，仍遵守访问控制、作息和忙碌限制。图片和文件沿用原来的会话图片缓存目录；清理时跳过尚未交给主模型的附件和正在处理的附件，交付后待本轮结束再恢复普通缓存规则，不设分类器专用目录或保留期。

分类器看图另存宿主附件引用，图片字节交给宿主附件存储管理，不以内联 base64 形式重复写入待交付正文。重启后可在后续判断中继续附带旧图片；仅供分类的图片不受主会话本地图片缓存清理影响。旧格式中没有图片引用的已准备记录不会自动重新下载。

只有主会话的 `followup()` 成功接纳后才删除待交付正文。这表示已进入主模型处理，不表示模型已生成回复或 QQ 已发送成功。宿主接纳与本地保存不是同一个事务，进程恰好在两者之间崩溃时，重启可能再次交付；当前不承诺跨进程崩溃的严格恰好一次。

当前待交付消息没有条数上限，尚未交付的附件也会保留，空间占用会随积压增长。此前仅依赖 DSH 自动压缩的安排不能覆盖一次新增超大输入；后续改为交付前检查容量、先压缩已有历史、默认左截断积压，并提供可选分批摘要，见[新方案](group-message-design.md)。历史消息的远端附件可能过期，保留源事件不能保证远端永久可下载。

已接纳消息保留最近约 4096 个去重 ID，待交付消息始终保留去重依据。坏记录不会被空状态覆盖；对应文件保留并报错，修复后重启重新加载。关闭功能不继续分类或交付旧消息；普通缓存清理仍读取待处理附件名单，避免误删。

## 后续开发顺序

记忆基础已按[记忆整理方案](memory-design.md)接入；部署使用官方 0.2.2-rc.2，并实测语义识别。先按[消息调整的四个批次](group-message-design.md#6-分四批实现)推进，再在统一状态区基础上实现下列情绪功能。记忆维护与情绪经历识别后续共用一次分析入口，状态和计分分别保存；重读旧记忆不重新触发经历。

1. 六情、六欲、逐人好感与变化记录；把原文初值和计算规则变成可配置参数。
2. 识别聊天经历、按可信来源归因，通过临时末尾状态区提供当前数值与表达要求；接入满足渠道与内容消费。
3. 完整作息、逐人求助、主动聊天、心愿、不满记录、满值事件；三种冷落/断联机制各自可选。
4. 页面、曲线和查询；集中检查重复计分、跨日、恢复、开关残留、无法解除状态和跨会话泄露。

上述情绪与关系功能目前尚未实现，不能将消息判断功能视为整个情绪系统已完成。自然程度由实际使用反馈评估。
