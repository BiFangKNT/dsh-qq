# 记忆整理方案

状态：记忆存储、工具、自动维护、迁移与末尾状态区已接入；使用未修改的 DSH 0.2.2-rc.2，见[末尾状态区接入](host-transient-context.md)。情绪计算未接入，真实部署与模型语义效果待实测。更新：2026-11-12。配置见[配置说明](configuration.md#上下文--人设--记忆)；情绪系统接入安排见[开发安排](emotion-system-development.md)。

## 要解决的问题

现有话头、便签、事实卡和群词典分别维护，入口和读取时机不一致。尤其 `便签.md` 依靠聊天模型自行覆盖，换 session 时却会再次注入：完成信息没写回文件，过时事项就被反复带到后续 session。把两个文件合并或加一句“记得更新”的提示词不能解决这个问题。

这次整理统一记忆的维护和读取，移除按 token 阈值提前换 session 的机制，不增加独立服务，也不取消已有日记、群词解释等能力。

2026-11-12 补充：[群聊触发与消息交付调整](group-message-design.md)尚未实现，将单独补上源消息保存、处理进度和容量检查。它不依赖可关闭的 `chatLog`，不改变本文的 system 锁定、末尾状态区和事项维护规则；截断未提供的消息不能被当作已读或已识别的经历。

本文用“当前事项”指新设计中持续跟踪的进展、承诺和未完成事项；“旧便签”专指原来的 `便签.md`、`交接.md` 及相关首轮注入机制。用户指出的旧便签痛点，应通过新功能自动更新事项状态来解决，不是继续维护旧文件。旧便签机制退役，文件仅备份、迁移和按需查阅，不能继续参与自动读写。

## 保留哪些内容，谁来维护

| 内容 | 谁维护、何时维护 | 怎样使用 |
| --- | --- | --- |
| 聊天原文 `聊天记录/` | 插件在收发消息时自动追加；沿用现有 `chatLog` 开关 | 查询细节、核对来源；不整份自动塞进每轮请求 |
| DSH 压缩摘要 | DSH 自动或手动 compact 时生成并保存在宿主 session 中 | 当前 session 自动使用；插件不另造摘要文件，不把 compact 当作新 session |
| 当前事项 | 插件在每轮结束后自动检查新增、进展、完成、取消和失效；用户也可显式修改 | 提供仍有效的当前进展、承诺和未完成事项，不是永久提醒 |
| 长期记忆 | 用户要求记住的事实、已确认的群词含义由统一工具维护；自动维护可根据明确证据提出更正或失效 | 末尾状态区提供当前聊天相关的有效事实，详细内容与旧版本按需查询；未确认内容不能当作事实 |
| 私聊中的群聊近况 | 保留现有从群聊天记录摘取近况的能力；由程序在请求前检查 | 获得授权后在末尾状态区提供最新相关内容；不冒充 DSH 摘要或长期记忆 |
| 日记、索引、项目、随笔 | 保留按需文件工具；日记脚本只有用户配置计划任务后才定时运行 | 查询或用户指定时使用，不要求每个聊天都维护整套文档 |
| 共享记忆 | 继续由显式启用的共享工具读写 | 不自动收集所有聊天的记忆；共享对象和范围由程序权限决定 |
| 情绪、好感、求助等运行状态 | 后续情绪模块根据经历和时间更新 | 程序状态负责计算；文字记忆不作为计分账本 |

“当前事项”和“长期记忆”是两个用途，不再对应多套互不相通的文件工具。内部每个机器人、每个私聊/群用一份 `memory.json` 保存两类条目和维护进度；统一工具返回人可读的内容，查询页面使用同一份数据。不再创建或维护新的 `便签.md`，也不同时维护 JSON 和数份 Markdown 正本。原有日记、聊天原文等仍是文件，不要求迁入此存储。

逻辑归属为机器人身份 + 私聊/群 + 对方/群号，与模型 session ID 无关；联系人和消息来源另有明确标识。换 session、compact、重启不清空记忆。已有工作目录继续使用，迁移时增加机器人身份隔离，不能因两个机器人复用目录而共享记忆。

## 当前事项必须自动更新

### 更新流程

1. 主模型本轮处理结束后，插件自动发起一次只读的记忆维护调用。它读取当前有效事项、上次维护后新增的已交付消息、本轮工具结果和实际发送结果，返回新增、修改、完成、取消或待核实的条目变更。复用可配置的模型/provider，不另起常驻服务，不要求聊天模型主动调用工具才能完成维护。
2. 程序校验变更中的条目 ID、版本和依据，再一次性保存条目及处理进度。维护调用不能执行工具、发送 QQ 消息、改 system 或改写已有主 session 历史；下一次请求从已保存的数据生成末尾状态区，其输出不当作下一条聊天再次触发维护。
3. 下一轮正式请求前等待本聊天已排队的维护完成，并处理明确的到期规则。新建 session 后也读取这份最新状态，不读取前一 session 已拼好的事项文本，更不读取旧便签文件。维护与用户显式修改串行执行；过期版本的结果不能覆盖较新的完成或取消。
4. 无新增证据时不反复调用模型。同一批消息和变更有处理进度与去重依据，重启后继续未完成工作。模型工具可以立即记录用户明确的修改，回合结束的自动维护仍检查剩余事项。

每轮维护是一项明确的后台工作，有成功、失败和待处理状态，不能用“提示模型记得整理”代替。维护所需调用会增加模型成本；后续情绪经历识别接入后，可在同一次识别中输出记忆变更和情绪经历，但两者分别保存、分别去重，不新建两个重复分析流程。前置分类器保持只读，不承担记忆维护。

### 完成与失效

每条当前事项至少有稳定 ID、内容、状态、创建/更新时间、有效期或下次核实时间、最近核实依据。状态为进行中、完成、取消、待核实或过期。完成、取消和过期条目保留供查询，不再作为当前事项自动提供。

- 用户明确说“已经做完”“不用了”“改成另一件事”，自动维护应更新原条目，而不是另加一条矛盾记录。助手说“我会做”只算承诺；生成了“做完了”的正文不等于工具已成功或 QQ 已发送。
- 文件写入、发送等程序能确认的结果，由成功结果支持对应步骤完成；不能据此推断用户线下已经完成另一件事。含义含糊时转为待核实，不猜测完成，也不继续当作确定的未完成事项催促。
- 当轮话题结束就收起临时进展；有明确日期/条件的承诺按该条件保留，并在约定时间后核实，不能仅因换了 session 就消失。
- 没有明确期限的当前事项，默认 24 小时没有新证据就转为待核实，停止自动提供。24 小时是可调整的工程默认值，不是“事情已经完成”的判断；查看、注入、compact、重启、重复提到旧记录均不能刷新有效期。只有新进展或用户重新确认才能续期。
- 待核实条目不在每个新 session 自动出现，也不自动循环发问。用户重提该事或主动查询当前事项时，再按当前消息和原始依据核实；旧摘要、旧便签和助手自己复述不能单独让它重新变成进行中。

例：用户说“周六提醒我做头像”，记录带日期的事项。周六用户说“头像已经做完了”，本轮结束后自动标记完成；下一次及再后续的新 session 都不再把“做头像”当作未完成承诺。若用户只说“先不说这个”，不认定完成；到核实时间后收起，而不是永久强调。

### 读取方式：统一末尾状态区

当前事项、相关长期记忆、授权的群近况，以及情绪、好感和场景要求，统一在每次请求的全部输入末尾提供一份当前有效内容。它是本次请求的临时资料，不进入锁定的 system，本次请求通过官方快照提供，响应提交后以空节点替换，后续模型输入及 compact 不含旧快照。原始快照与清理操作仍在日志中保留用于回放。下一次请求提供最新状态，不累积旧状态作为模型输入。普通聊天里已经谈到的经历、事项与事实仍属于聊天原文，不因此删改。

正常请求的逻辑顺序如下；工具 schema 是单独的请求字段，其最终编码由模型适配器决定：

```text
固定 system、固定工具定义
已有聊天：用户消息、回复、工具调用及工具结果；压缩后为宿主摘要与保留消息
本次用户消息
末尾状态区：有效当前事项、相关记忆、当前情绪与关系、场景及表达要求
```

状态区明确标记插件来源与各部分的用途，内容是背景资料，不冒充用户的新任务，也不能改变 system 或工具权限。稳定条目 ID 可用于查询与更新；条目版本供工具安全更新，完整修改历史留在存储中；给模型的时间只在理解期限或来源确有需要时出现，不添加每次变化的采样时间。

当前事项提供完整有效列表；完成、取消、过期和待核实项不作为未完成任务提供。列表为空时明确写“当前没有已记录的有效跟进事项”，不能直接省略；读取失败或维护未完成则明确标为未核实，不能伪装成空列表。旧聊天、旧快照或摘要中出现的事项不因此恢复；本轮用户提出的新要求仍正常处理。长期记忆只提供当前聊天相关的有效事实，未选入不代表被删除；需要历史或更多细节时用统一工具查询，不把整个档案塞进状态区。

跨轮跟进以最新有效事项为准，事实更正以有依据的最新记录为准；固定规则明确旧便签、助手复述和旧摘要不能覆盖这些结果。完成记录、旧版本和修改依据保存在存储中按需查询，不自动堆入上下文。迁移前已经进入旧 session 的快照仍属于旧历史，不能仅凭切换读取入口就宣称已清除；遵循现有同步选项更新固定规则，必要时由用户选择压缩或新建 session。

每次请求从已提交数据生成一致的状态区；在该次请求发出后不改动其内容，网络重试沿用同一份快照。工具成功修改事项或记忆，先由真实工具结果告知模型，下一次工具续调读取最新已提交状态；不重写此前工具结果。主动轮次也使用同一读取入口。状态区放在完整工具调用与结果之后，不能插入两者之间。读取不重复计分、不额外调用识别模型。

成功 compact 后沿用宿主摘要与保留聊天，下一次请求仍从存储生成当前状态，不从摘要恢复事项、不续期。compact 失败、换 session、重启和闲置恢复也不改变存储中的完成状态。状态快照每步骤提供并清理，因此不另设初始记忆注入标记或跨 session 的快照交付进度；自动维护和工具写入仍保存处理进度、来源 ID 与版本，防止重复写入。

### 情绪与其他动态资料

情绪、对当前发言人的好感、求助阶段和当前表达要求使用同一末尾状态区。只提供当前聊天可见的必要数值和要求，不列所有联系人的关系、不泄露其他聊天原因；详细变化曲线保存在程序中，按需查询。换人、情绪恢复、功能关闭和特殊状态结束直接反映在当前值中。

群近况、已确认群词和表情包资料也按授权提供最新相关内容，具体可否访问或发送由程序与工具实时检查。字段和顺序稳定，内容简短；不为展示权重每轮随机抽取或重排资料，不增加向量服务。记忆的相关内容选择先沿用聊天归属、对象和明确查询条件，更多检索方式在实际需要时再增加。

分类器不能只读取持久聊天历史：它还要通过同一只读入口获取当前状态区，与主会话完整有效聊天、锁定 system、工具定义及待处理消息共同作为判断背景。分类器不执行维护、不推进计分、不消费主会话输入，也不把状态区另存成主会话消息。

这项设计接受末尾缓存重新计算。两次请求可复用的范围止于第一个不同的位置：上一轮的状态区被移除或替换后，旧状态后生成的回复和工具续调也不能复用原缓存；不是严格只有状态区本身失效。把状态放在全部输入末尾，能保住它之前的长历史，同时避免历史状态不断堆积。状态长度小幅变化不会反过来改变此前的前缀。

### 故障处理

维护调用失败或存储写入失败时，保留原数据和未处理进度，记录日志，并在查询中显示“有新消息尚未整理”。下一次正常调度处理未完成工作，不因故障丢弃用户消息或阻断正常聊天。

有尚未核对的新消息时，尚未更新的事项不能继续被包装成最新未完成事项：状态区暂不提供这些条目，明确标记“当前事项尚未核实”，不以空列表或旧快照代替。原始聊天和宿主摘要仍可用，用户可以查询原条目及其未核实状态。首次恢复成功后，再依据最新证据决定继续、完成或取消。存储损坏时保留文件、记录错误，不能写入空状态覆盖；超时或失败也不能静默当作“没有变化”。

程序能保证维护会被调度、成功变更会保存、终态不会反复注入；语义识别仍可能出错。统一工具必须允许用户更正，不能宣称自动判断永远准确。

## 长期记忆怎样维护

事实卡与群词典使用同一个读写入口，按稳定聊天标识保存。保留事实、群内用语、待确认三种内容标记，不再靠显示名称或 Markdown 标题决定数据归属。

- 事实仍以用户明确要求记住为新增入口；已确认的群词含义可以记录。程序扫描到“没懂”等表达只产生待确认候选，不能自动补造含义。现有候选收集能力保留并接入统一维护，不另存一本词典。
- 统一支持查询、新增、更正和移除；每条保留来源、更新时间及变更原因。自动维护根据明确新证据更正过时事实，含糊时标为待确认。
- 有时效的事实携带有效期，不能用“长期记忆”绕过当前事项的退出规则，例如“今天头疼”不能永久生效。完成事项只有值得长期保留且符合记录规则的事实部分才进入记忆，不把所有已完成事项复制进去。
- 在末尾状态区提供当前聊天相关、允许读取的有效内容，删除、更正与失效在下一次请求中反映；待确认项按需查询并明确标记，不与已确认事实混写。固定 system 只放使用规则，记忆变化不触发提示词同步，不通过删改聊天历史体现变化。
- 为后续情绪需求预留重要度字段；情绪只影响权重，不改记忆正文、有效期或完成状态，不通过减少条数冒充重要度。具体权重与读取预算在对应功能实施时确定，不先加向量库或额外检索服务。

## 压缩与换会话

正常长聊交给 DSH compact，删除插件按 token 比例或固定 token 数提前换 session 的机制。`contextSwapRatio`、`contextSwapMinTokens` 和对应的主动切换路径退出；旧配置迁移时忽略并说明。`contextMemoryKeep` 随“换会话前另存最近原文”的路径退出，不改变 `chatLog` 开关。已有 `压缩记忆/` 文件保留为历史档案，不再持续生成重复副本。

一次新增的积压也可能超过窗口，不能仅依赖宿主步前检查。后续按[消息调整方案](group-message-design.md#4-提交前检查是否装得下)在交付前检查容量：本次待交付消息暂不进入 compact，先压缩已有历史，再重新组装背景和触发消息。默认左截断、可选分批摘要；这不是重新引入自动换 session。

用户通过设置页或 `/new`、`/reset` 明确新建 session 时才切换。切换与记忆维护共用本聊天的串行队列；等待当前回复和已排队维护结束，再读取最新有效事项和长期记忆。模型维护失败遵循上面的未核实规则；若连维护进度都无法落盘，则保留当前 session 并报告切换失败，修复存储后再切换，不能丢失旧会话尚未保存的维护依据或退回旧便签。

compact 成功不代表事项完成，也不刷新事项有效期；压缩摘要只负责当前上下文。真实上下文超限或压缩错误应记录并明确反馈，保留当前 session 和原消息，不静默 reset，不用旧便签兜底重建，更不能无限重试。用户仍可明确选择压缩或新建会话。

私聊中的群聊近况与 DSH 摘要分开命名和实现；它是跨聊天资料，不因为“统一记忆”扩大读取范围。共享记忆仍需显式开启，群资料不能因此自动进入任意私聊。新设计接入前要审查现有近况读取的授权范围。

## 请求前缀与缓存检查

目标是保留固定 system 与已有长历史的相同前缀，不承诺服务端一定命中缓存。DeepSeek 的缓存依赖可复用的相同前缀，实际命中还受服务端缓存单元与保留情况影响，见[官方说明](https://api-docs.deepseek.com/guides/kv_cache/)。事项、相关记忆和情绪等资料统一在请求末尾动态更新，接受从上一轮状态位置起的尾部重新计算，不要求为了缓存保留过时状态。

| 检查项 | 检查结果与设计要求 |
| --- | --- |
| 当前事项、长期记忆 | 统一在末尾状态区提供有效事项及相关有效事实，完成与旧版本留在存储中；旧状态不留在后续模型输入中，不改写已有聊天 |
| 情绪、好感、场景要求 | 每次请求在全部输入末尾提供一份简短的当前状态，动态替换，后续模型输入不保留历史快照。换人、情绪恢复、功能关闭或特殊状态结束都反映在当前值中；数值曲线留在程序与查询中。接受旧状态位置起的尾部缓存失效，不影响更前面的相同前缀 |
| 事实卡、群词典、群近况、表情包资料 | 统一在末尾区提供最新相关内容，响应后通过官方替换接口清理快照；不能重复沿用旧文件注入入口，也不改变锁定 system |
| 时间、睡眠、主动提示、附件与引用 | 当前时间放本条新输入或新插件事件里，历史中的时间、引用、附件路径保持原值；不为旧消息重算“现在”“几分钟前”、重新下载生成随机路径或替换附件表示。同轮工具续调不重复生成时间提示；主动意图只提交一次 |
| 工具定义 | 保持相同工具集的名称、描述、schema 和顺序稳定；时间、剩余额度、表情库存、情绪不拼进工具定义。权限变动必须正确执行，不能为了缓存保留越权能力；确需改变工具集时接受该处前缀变化 |
| 渲染与排序 | 相同内容使用稳定条目顺序、字段顺序、空白与换行；不随机抽样，不每轮生成无业务含义的 UUID 或更新时间。状态区内容相同时保持相同文本。禁止重排历史以优化“重要度” |
| 分类器、记忆维护与情绪经历识别 | 独立请求使用各自固定指令、稳定字段顺序，并把本次新增输入放在后部；不把运行时间、重试次数等塞进固定指令。当前分类器输入还含主上下文与待处理消息，队列消费或 compact 会改变它的公共前缀；其缓存成本单独评估，不牺牲完整输入来假造高命中，也不污染主 session |
| compact、新 session、强制同步及模型/预设变化 | 属于明确允许的前缀变化，不伪装为完全保留缓存；普通配置保存、重启恢复、页内状态刷新不能触发相同变化。不得为减少追加记录而自行提前 compact 或换 session |

提交 `563cf06` 已锁定主会话完整 system，显式强制同步规则保留。新版 `@deepseek-ai/dsh-system-prompt@0.2.2-rc.2` 分别管理固定 system 与动态 context；完整 system 的恢复读取消息节点，不再读取旧请求头的 system 字段。

动态状态采用官方 `prompt.context()` 和已记录的消息替换：每步骤捕获一次，普通重试复用，工具续调刷新。响应提交后将包含 QQ 状态的快照替换为空 developer 节点，后续模型输入和 compact 不含旧状态。日志仍保存原始快照与清理记录，可还原当时请求。无需修改宿主，接入、版本限制和测试见[末尾状态区](host-transient-context.md)。

同一 QQ 会话的其他 runtime-context 会随官方合成快照一起清理，并在下一步重新提供；其他 agent 不受影响。替换可能导致旧状态位置之后的尾部缓存失效，不为缓存命中延迟事项更正或权限变化。

验证分两层：模拟请求检查相同历史前缀、状态区位置与历史隔离；真实 DSH 检查最终 provider 请求中的 system、工具及 messages（包括工具续调、compact 和重启恢复）。比较时包含模型可见角色、内容和附件表示，不只比较拼出的字符串；不得打印凭据、私人聊天或推理。真实模型的命中/未命中 token 仅用于观察结果，不能单次命中低就判定程序有错，也不能用 mock 宣称缓存一定命中。

## 与情绪系统怎样配合

记忆条目、情绪状态、情绪变化记录各有明确用途。心情、好感、等待谁回应、求助阶段由程序保存；它们可以产生当前事项，但对应流程结束时必须由程序同步关闭相关条目。心愿或不满不能因为旧记录被读到就重新开始。

同一真实经历有来源 ID，重新读取记忆、compact、换 session、恢复进程或维护重试都不重复计分。跨聊天只能共享允许的当前表达要求，不把其他聊天的原话、人物和原因带过去；好感不增加记忆读取或管理权限。

## 旧数据怎样迁移

先保存原文件备份，按来源标记导入，成功后再切换统一入口；同一次迁移可重复执行但不能重复导入。读取或写入失败保留原文件并报错，不能用空状态覆盖。

| 旧内容 | 迁移去向 |
| --- | --- |
| `话头.md` 未完成条目、`便签.md`、旧名 `交接.md` | 当前事项中的待核实条目；相同内容合并，语义相近的条目待用户查询核实，不直接恢复为当前任务 |
| `话头.md` 已完成条目 | 完成记录，不自动提供 |
| `事实卡.md` | 长期记忆；保留原全局/聊天归属，无法匹配稳定聊天身份的部分待人工核对，不分发给所有聊天 |
| `群词典.md` | 长期记忆中的群内用语及待确认项，保留所属群 |
| 日记、项目、随笔、聊天记录、旧压缩记忆 | 原样保留，仍可按需查询 |

旧便签没有可靠的完成状态或核实时间，不能仅凭文件存在就认定仍有效。首次迁移的待核实项不自动注入后续 session；可通过一次迁移查询查看、确认或关闭。切换成功后所有自动读取入口停止读取旧便签文件，避免新旧机制同时生效。真正的全局事实保留共享用途，但必须先明确适用的机器人和读取范围。

旧 `qq_pin` 的写入口和要求模型维护 `便签.md` 的提示同步退役，由统一工具接替。旧 session 中尚未同步的固定提示可能仍提到旧文件：旧写入口不再写旧文件，也不能依据这类旧指令重新导入；固定规则按现有新建、compact 或强制同步约定更新，不在普通请求中偷偷修改 system。迁移完成后不安排任何更新旧便签文件的后台任务。

## 实施顺序与验收

1. 移除提前换 session 和上下文错误自动 reset，保留宿主压缩及用户明确切换入口；验证原消息和 session 不丢失。
2. 实现统一存储、当前事项状态和工具，迁移旧数据，切断旧文件读写及注入；同步更新固定规则，新旧 session 遵循现有 system 同步约定。
3. 接通宿主临时末尾资料接口，再接入每轮自动维护与统一状态区；验证完成、更正、到期、维护失败与恢复，切断其他重复资料入口。达到这些条件后才算解决旧便签反复强调的问题。
4. 接入长期记忆与现有群词候选，统一权限、查询和更正；随后继续情绪系统开发。

测试检查客观逻辑：已完成事项跨多次新 session 不再作为未完成事项提供；完成后旧版本更新不能复活条目；成功/失败 compact 都不续期；明确未来日期的事项不会因 24 小时规则提前消失；无期限且无人重新确认的条目收起；维护失败不重复提供未核实旧事项，恢复后正确更新；重复调度与崩溃恢复不重复写入；迁移失败不丢文件、迁移完成后旧文件不再被更新或注入；分类器仍只读，不同账号和聊天不串记忆，重读记忆不重复影响好感。

模型能否从各种含糊表达中准确识别完成，属于真实使用的语义效果；用带明确证据和固定维护结果的用例验证程序生命周期，再由用户反馈补充识别样例，不以主观聊天效果代替逻辑测试。

状态区与缓存的客观检查包括：每次请求仅有一份最新有效资料，位于全部输入末尾，不积累旧快照，不进入 compact 输入；空事项列表、读取失败与维护未完成的表示不同；旧摘要中的已完成任务不恢复；相关记忆未被选入不当作删除。状态变化或长度变化不改变更前面的 system 与历史；同次请求重试使用相同快照，工具修改后的下一次请求读到已提交内容；工具调用和结果不被打断；新建、compact 和重启后均读取最新存储，完成状态不丢失、不续期；表情库存变化不修改工具 schema；权限变化立即生效；分类器包含当前状态区且保持只读。明确区分前缀稳定性检查与服务端实际缓存命中，允许旧状态位置起的尾部重新计算。
