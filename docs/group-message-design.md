# 群聊触发与消息交付调整

状态：第 1、2 批已实现，第 3、4 批尚未实现。更新：2026-11-12。

这次解决三件事：程序不再把沉默变成回复；群聊何时处理消息更容易理解；积压消息既不反复提供，也不会一次塞爆上下文。情绪计算、长期关系和末尾状态区的设计不变。

`/cwd` 因普通路径被外发检查误拦的问题已修复。敏感内容检查保留，命中后给出固定反馈，不增加模型请求。下面的调整另外分批实现，不表示当前代码已经具备这些行为。

## 1. 模型没有正文，就不发送

- 删除从 reasoning 中提取文字作为正式回复的逻辑，任何触发方式都不能使用这条路径。
- 正文为空、被清理为空或明确选择沉默时，不补一句回复。沉默不算发送失败。
- 保留现有 `[SILENT]` 约定；它只控制是否外发，不阻止本轮正常完成。
- 延迟处理、恢复队列和分类器放行都不自动变成“必须回复”。被 @ 时是否允许沉默，仍由对应设置决定。
- 普通群聊的沉默说明使用末尾状态区，不再随每条用户消息写入历史。固定使用规则遵守已有 system 锁定与同步约定；旧历史不批量改写。

第 1 批已落地：回复出口只使用正文，不从 reasoning 补话；群消息补发、分类器放行和队列恢复保留原来的沉默规则。沉默说明在宿主取出本轮消息时加入末尾状态区，工具续调和网络重试沿用本轮要求；响应后移出后续输入，不进入 compact。下一条消息重新确定是否允许沉默，主动消息入口不继承普通群聊说明。第 2 批已移除保活和其他旧唤醒旁路。

分类器一次交付多条消息时，检查整批的结构化自身 @；只要其中一条仍需回复，就保留整批的回复要求。开启“被 @ 也允许沉默”时，这些 @ 不再要求回复。名字、引用和关键词不再改变触发或回复要求。积压容量处理仍属于第 3 批。

## 2. 群聊什么时候处理消息

默认仍要求 @。保留一项“必须 @才接话”的设置，允许按群覆盖；原来的免 @ 群名单迁入这项设置，不再让用户同时维护两种含义相近的配置。

“必须 @”是启动普通群聊主模型的硬限制，名字、引用、问句、概率、保活和分类结果都不能绕过。开启分类器仍逐条判断合格消息，未被 @ 的消息可以成为后续背景，但不能因此启动主模型。

| 必须 @ | 分类器 | 普通群聊行为 |
| --- | --- | --- |
| 开 | 关 | 只有结构化的自身 @ 才触发 |
| 开 | 开 | 自身 @ 且分类器放行才触发 |
| 关 | 关 | 新消息等待合并后交给主模型，由它决定是否发言 |
| 关 | 开 | 分类器放行时交给主模型，不再额外安排一次定时观察 |

分类器默认关闭，使用独立 session，保持只读，不修改主会话参数、system 或历史。没有启用它时，不产生分类模型请求。

不要求 @且关闭分类器时，只增加一项“普通群聊处理间隔”：

1. 第一条待处理消息开始计时，后来的消息合并，不重置计时。
2. 到期处理本次范围内的消息；没有新消息就不运行。
3. 自身 @ 或自定义触发词可以提前结束等待，首条消息命中也立即处理。触发词默认空，按当前消息文字包含匹配、区分大小写，不匹配引用、转发、历史和 @他人的昵称；命中不强制回复，不替代“必须 @”或绕过分类器。主模型忙时等当前轮结束，同一会话始终串行处理。
4. 固定本次处理的最后一条消息，处理期间的新消息留到后面，不被旧任务清空。
5. 模型可以沉默，但观察本身仍消耗一次主模型请求。

第 2 批已落地，普通群聊处理间隔默认 30 秒，可通过 `groupMessageIntervalMs` 修改。旧保活、名字/问句/关键词/概率唤醒和保活窗口额度退出；旧回复间隔不与新等待重复叠加。保留权限、同类机器人限制、作息和必要的发送限流；全局 `requireMention` 保留原值，旧 `groupFree` 读取时迁入 `groupMentionOverrides: false`，已有明确按群值优先；其余旧唤醒字段忽略并在下次保存时移除，详情见[配置说明](configuration.md#群里怎么说话)。待交付群消息复用现有持久队列，等待时重启、切换会话或开关后按当前设置继续，第三批再统一完整消息保存和容量处理。

群聊命令仍必须结构化 @自身，不受普通聊天开关或分类器放行影响；私聊命令沿用现有入口。历史补入只作为背景，不重新执行其中的命令。审批和问答回复沿用原控制通道。

主动聊天、求助等独立功能仍受各自开关、额度和作息控制，不借普通消息合并计时发起。看过群消息不自动算与每个人发生互动，也不自动结束等待某人回应。

## 3. 按真实消息顺序提供背景

对通过现有访问与屏蔽规则的源消息，按机器人身份和群/私聊分别保存消息 ID、时间、发言人、源事件和处理后的正文。没触发主模型不代表消息被丢弃；保存源事件不绕过媒体屏蔽，也不承诺远端附件永久可下载。

触发时提供上次处理位置之后、本次范围之内的消息，按时间顺序区分背景与本次触发消息。已经进入主会话的内容不因“最近 N 条”而每轮重复附带。`historyLimit` 和普通群聊最多 30 条的临时补历史逻辑退出；已进入主 session 的历史继续交给宿主 compact，不为了减小输入另建 session。

项目整理第三批已将框架固定定义经现有提示词组装链放入锁定 system，正文统一维护在 `src/prompts.js`，只说明消息结构、来源、入口和工具职责；事项、事实、情绪等动态资料继续放在末尾状态区。新版不再生成插件旧 `AGENTS.md`，对精确匹配的旧模板先备份再停用；未知或手改文件保留并报告冲突，详见[迁移说明](configuration.md#工作目录指令与升级)。已有历史中的旧指令不批量改写。这不表示本节的完整消息流或容量处理已经完成。

框架定义更新沿用现有 system 锁定、快照与四种同步选项，不改变 QQ 消息顺序或处理位置，也不参与经历计分。宿主仍可能提供用户自己的工作目录指令等辅助消息，应按来源识别并纳入总预算，不能当成新的 QQ 发言；这不要求关闭其他会话的官方指令功能。

记录要分清三件事：消息已经进入主 session、模型本轮已经正常处理、QQ 是否发送成功。不能只用一个“已发送”位置代替：

- 主模型正常结束后推进本次处理位置，包括沉默的轮次。
- 请求失败保留未完成范围；已经写入主 session 的消息不能再次盲目追加。工具已成功执行的结果也不能因重试而重做。
- QQ 发送失败单独保存结果和发送进度，不靠重新运行整轮模型恢复。发送结果不确定时明确记录，不能承诺严格恰好一次。
- 左截断跳过的范围单独记录为“未提供”，不能标成模型已读，也不在下一轮自动塞回。原始记录保留，模型和用户可按权限回查。
- 重读背景、摘要、重试和恢复都不重复计分；未提供的原文不能被当成已经识别的经历。内容缺失时，不能把已有事项宣称为刚刚核实。

这些记录不能依赖可关闭的 `chatLog`。实现时明确待处理消息、已处理记录和附件的保存与清理规则：待处理内容不能被普通清理误删，原文清理要有明确范围，原始消息保留与附件缓存期限分开说明。不能用无限增长的内存列表代替持久记录，也不能悄悄清理后仍声称完整可查。

切换或重建 session 时，已在旧会话完成的内容不自动全部重放；尚未交付的范围继续保留，执行前重新确认目标 session。重启、关闭分类器、修改触发设置和卸载时取消旧等待任务，恢复后按当前设置重新安排，不让旧定时器把消息送进错误会话。分类器旧记录迁移时保留消息 ID、判断结果和处理进度，不能丢消息或重复交付。

## 4. 提交前检查是否装得下

token 计数统一计算、缓存和复用，不为每个功能另做一套。新增消息或内容变化时更新计数；选择消息范围可利用累计计数，发送前再检查最终组装输入。分类器同样在请求前检查容量，但不能借此触发主 session 压缩或改写历史。

预算包含 system（含框架固定定义）、工具、当前有效历史、待交付消息、图片、宿主实际注入的其他辅助内容和末尾状态区，并留出输出和压缩指令的空间。辅助内容即使在插件选择消息范围之后才由宿主加入，也必须在最终组装检查中计入，不能当作免费空间；同一内容不重复计数。窗口大小、输出预留和宿主压缩配置以实际模型为准，不能写死为 1M 或固定 80 万 token。本地计量仍可能与服务端有差异，不能把文本分词结果当成完整请求的精确价格。

DeepSeek 的 tokenizer 文件和消息模板按兼容的模型系列复用，不按每个日期版本复制一套；以对应模型的官方实现为依据，不拿旧模型的 tokenizer 宣称新模型计数准确。切换计量规则时使旧计数缓存失效，不自行维护分词算法。兼容依据见[官方 tokenizer 文档](https://github.com/deepseek-ai/deepseek-recipe/blob/main/docs/tokenizer.md)。

普通交付按下面的顺序执行：

1. 确定本次处理范围，把待交付背景和本次触发消息暂存在插件中，先检查总大小。
2. 超过安全预算时，等待主会话空闲，通过宿主正式接口压缩已有历史。本次待交付消息不先塞进历史，也不交给这次 compact。
3. 压缩成功后，沿用现有规则同步 system，再按最新历史和状态重新计算空间。
4. 优先保留本次触发消息原文；默认从积压左侧移除较早的完整消息，保留装得下的最近部分。不截断工具调用与结果对。
5. 告知模型哪些消息范围没有提供，再把剩余背景和本次触发消息交给主模型，正常回复或沉默。compact 本身只生成摘要，不代替这次聊天请求。

没有可压缩内容时继续按剩余空间选择积压，不能反复调用无效 compact。压缩失败、输入预算本身不足或单条触发消息仍然超限时，保留原消息，记录并反馈原因；不静默 reset、截掉触发消息或无限重试。分类器输入过大时采用相同的默认左截断选择规则，并标明缺失范围；它不会因此推进主模型的处理位置。

左截断会遗漏尚未读取的内容，这是默认策略的明确取舍，不能继续承诺任意积压都会完整进入模型。性能验证测量首次载入、日常新增、超大积压和切换模型的开销，不预先承诺具体毫秒数。

## 5. 可选：分批摘要

默认关闭。开启后，装不下的较早积压按时间分批整理成摘要，最后把摘要、能保留的近期背景和本次触发消息原文一起交给主模型。每个摘要请求及最终请求都必须装得下；它会增加模型调用和延迟。

摘要过程不发送聊天、不执行工具，不直接写成长期记忆或情绪计分结果。保留来源范围和已完成进度，避免重启后反复摘要。失败时保留进度、明确报错，不偷偷改回左截断。摘要不能保证保留全部原文细节，原始记录仍用于回查。

## 6. 分四批实现

每批只实现该批行为、对应设置迁移和必要测试，通过后再进入下一批。

当前先完成[项目整理的三批](project-audit.md#分批执行)，再继续本表第 3、4 批。项目整理不另造完整消息队列；消息保存、处理进度、附件保留和容量检查在本表第 3 批一起完成。资料检索改造在本表第 3、4 批之后单独实现，包含聊天私有资料和可选公共资料，不作为继续本表第 3 批的前置条件。

| 批次 | 改动 | 重点验证 |
| --- | --- | --- |
| 1. 沉默与回复出口（已完成） | 删除 reasoning 转发；修复延迟/恢复后变成必须回复；沉默说明放到末尾状态区 | 空正文不发送，reasoning 不外发，沉默正常结束，重试不改变沉默规则 |
| 2. 群聊触发（已完成） | 统一必须 @及按群覆盖；移除旧保活等旁路；关闭分类器时支持定时合并 | 四种设置组合、无消息不调用、@提前处理、持续来消息不无限延期、同会话串行、命令不被旁路 |
| 3. 消息保存与默认超窗处理 | 持久记录和处理进度；取消重复最近 N 条；统一计量、先 compact、默认左截断 | 顺序、去重、失败与重启恢复、跨账号隔离、超大积压、单条超限、跳过范围不冒充已读、未读附件保留 |
| 4. 可选分批摘要 | 在第 3 批基础上增加开关、摘要与恢复 | 每批及最终输入不超预算、来源可查、失败不丢进度、不执行工具、不重复计分 |

第 2 批完成时仍受旧消息保存限制，不能宣称已经实现完整消息流；第 3 批必须把保存与容量检查一起完成，不能先上线无限拼接。每批只验证客观逻辑和必要性能，真实 QQ、DSH 和模型兼容性另做集成验证；是否自然、是否值得接话由用户实际使用反馈。

完成这些调整后，再继续[情绪系统开发安排](emotion-system-development.md#后续开发顺序)中的情绪计算，不把这次改动扩展成整个情绪系统重写。
