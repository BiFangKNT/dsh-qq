# 群聊触发与消息交付调整

本文维护群聊触发、消息保存与容量处理的设计和边界。各批次状态与下一步统一见[开发进度与计划](progress.md#当前进度与下一步)。

这次解决三件事：程序不再把沉默变成回复；群聊何时处理消息更容易理解；积压消息既不反复提供，也不会一次塞爆上下文。情绪计算、长期关系和末尾状态区的设计不变。

`/cwd` 因普通路径被外发检查误拦的问题已修复。敏感内容检查保留，命中后给出固定反馈，不增加模型请求。下文描述消息链路约定；第 5 节为可选分批摘要设计，是否已落地以进度文档为准。

## 1. 模型没有正文，就不发送

- 删除从 reasoning 中提取文字作为正式回复的逻辑，任何触发方式都不能使用这条路径。
- 正文为空或明确选择沉默时，不补一句回复。沉默不算发送失败。只按 text/reasoning 结构、工具调用消息、明确沉默标记及敏感检查决定是否外发，不按语言、行首词、口吻或相似句删改正常 text；统一移除 `<text>` 包装并修剪首尾空白的行为保留。
- 保留现有 `[SILENT]` 约定；它只控制是否外发，不阻止本轮正常完成。
- 延迟处理、恢复队列和分类器放行都不自动变成“必须回复”。被 @ 时是否允许沉默，仍由对应设置决定。
- 普通群聊的沉默说明使用末尾状态区，不再随每条用户消息写入历史。固定使用规则遵守已有 system 锁定与同步约定；旧历史不批量改写。

第 1 批已落地：回复出口只使用正文，不从 reasoning 补话；群消息补发、分类器放行和队列恢复保留原来的沉默规则。沉默说明在宿主取出本轮消息时加入末尾状态区，工具续调和网络重试沿用本轮要求；响应后移出后续输入，不进入 compact。下一条消息重新确定是否允许沉默，主动消息入口不继承普通群聊说明。第 2 批已移除保活和其他旧唤醒旁路。

分类器一次交付多条消息时，检查整批的结构化自身 @；只要其中一条仍需回复，就保留整批的回复要求。开启“被 @ 也允许沉默”时，这些 @ 不再要求回复。名字、引用和关键词不再改变触发或回复要求。积压容量处理仍属于第 3 批。

## 2. 群聊什么时候处理消息

默认仍要求 @。保留一项“必须 @才接话”的设置，允许按群覆盖；原来的免 @ 群名单迁入这项设置，不再让用户同时维护两种含义相近的配置。

“必须 @”是启动普通群聊主模型的硬限制，名字、引用、问句、概率、保活和分类结果都不能绕过。开启分类器仍逐条判断合格消息，未被 @ 的消息可以成为后续背景，但不能因此启动主模型。

| 必须 @ | 分类器 | 普通群聊行为 |
| --- | --- | --- |
| 开 | 关 | 只有结构化的自身 @ 才触发 |
| 开 | 开 | 自身 @ 且分类器放行才触发 |
| 关 | 关 | 新消息等待合并后交给主模型，由它决定是否发言 |
| 关 | 开 | 分类器放行时交给主模型，不再额外安排一次定时观察 |

分类器默认关闭，使用独立 session，保持只读，不修改主会话参数、system 或历史。没有启用它时，不产生分类模型请求。

不要求 @且关闭分类器时，只增加一项“普通群聊处理间隔”：

1. 第一条待处理消息开始计时，后来的消息合并，不重置计时。
2. 到期处理本次范围内的消息；没有新消息就不运行。
3. 自身 @ 或自定义触发词可以提前结束等待，首条消息命中也立即处理。触发词默认空，按当前消息文字包含匹配、区分大小写，不匹配引用、转发、历史和 @他人的昵称；命中不强制回复，不替代“必须 @”或绕过分类器。主模型忙时等当前轮结束，同一会话始终串行处理。
4. 固定本次处理的最后一条消息，处理期间的新消息留到后面，不被旧任务清空。
5. 模型可以沉默，但观察本身仍消耗一次主模型请求。

第 2 批已落地，普通群聊处理间隔默认 30 秒，可通过 `groupMessageIntervalMs` 修改。旧保活、名字/问句/关键词/概率唤醒和保活窗口额度退出；旧回复间隔不与新等待重复叠加。保留权限、同类机器人限制、作息和必要的发送限流；全局 `requireMention` 保留原值，旧 `groupFree` 读取时迁入 `groupMentionOverrides: false`，已有明确按群值优先；其余旧唤醒字段忽略并在下次保存时移除，详情见[配置说明](configuration.md#群里怎么说话)。待交付群消息复用现有持久队列，等待时重启、切换会话或开关后按当前设置继续，第三批再统一完整消息保存和容量处理。

群聊命令仍必须结构化 @自身，不受普通聊天开关或分类器放行影响；私聊命令沿用现有入口。历史补入只作为背景，不重新执行其中的命令。审批和问答回复走独立控制通道：群审批只接受授权账号显式 @ 后的「通过／拒绝／取消」；群问答只接受本轮最后发言人显式 @ 后的答案，不接受其他成员代答。私聊审批与身份边界见[授权说明](persona.md#授权与称呼)。

主动聊天、求助等独立功能仍受各自开关、额度和作息控制，不借普通消息合并计时发起。看过群消息不自动算与每个人发生互动，也不自动结束等待某人回应。

## 3. 按真实消息顺序提供背景

对通过现有访问与屏蔽规则的源消息，按机器人身份和群/私聊分别保存消息 ID、时间、发言人、源事件和处理后的正文。没触发主模型不代表消息被丢弃；保存源事件不绕过媒体屏蔽，也不承诺远端附件永久可下载。

触发时提供上次处理位置之后、本次范围之内的消息，按时间顺序区分背景与本次触发消息。已经进入主会话的内容不因“最近 N 条”而每轮重复附带。`historyLimit` 和普通群聊最多 30 条的临时补历史逻辑退出；已进入主 session 的历史继续交给宿主 compact，不为了减小输入另建 session。

项目整理第三批已将框架固定定义经现有提示词组装链放入锁定 system，正文统一维护在 `src/prompts.js`，只说明消息结构、来源、入口和工具职责；事项、事实、情绪等动态资料继续放在末尾状态区。新版不再生成插件旧 `AGENTS.md`，对精确匹配的旧模板先备份再停用；未知或手改文件保留并报告冲突，详见[迁移说明](configuration.md#工作目录指令与升级)。已有历史中的旧指令不批量改写。

框架定义更新沿用现有 system 锁定、快照与四种同步选项，不改变 QQ 消息顺序或处理位置，也不参与经历计分。宿主仍可能提供用户自己的工作目录指令等辅助消息，应按来源识别并纳入总预算，不能当成新的 QQ 发言；这不要求关闭其他会话的官方指令功能。

记录要分清三件事：消息已经进入主 session、模型本轮已经正常处理、QQ 是否发送成功。不能只用一个“已发送”位置代替：

- 主模型正常结束后推进本次处理位置，包括沉默的轮次。
- 请求失败保留未完成范围；已经写入主 session 的消息不能再次盲目追加。工具已成功执行的结果也不能因重试而重做。
- QQ 发送失败单独保存结果和发送进度，不靠重新运行整轮模型恢复。发送结果不确定时明确记录，不能承诺严格恰好一次。
- 左截断跳过的范围单独记录为“未提供”，不能标成模型已读，也不在下一轮自动塞回。原始记录保留，模型和用户可按权限回查。
- 重读背景、摘要、重试和恢复都不重复计分；未提供的原文不能被当成已经识别的经历。内容缺失时，不能把已有事项宣称为刚刚核实。

这些记录不能依赖可关闭的 `chatLog`。实现时明确待处理消息、已处理记录和附件的保存与清理规则：待处理内容不能被普通清理误删，原文清理要有明确范围，原始消息保留与附件缓存期限分开说明。不能用无限增长的内存列表代替持久记录，也不能悄悄清理后仍声称完整可查。

切换或重建 session 时，已在旧会话完成的内容不自动全部重放；尚未交付的范围继续保留，执行前重新确认目标 session。重启、关闭分类器、修改触发设置和卸载时取消旧等待任务，恢复后按当前设置重新安排，不让旧定时器把消息送进错误会话。分类器旧记录迁移时保留消息 ID、判断结果和处理进度，不能丢消息或重复交付。

## 4. 提交前检查是否装得下

token 计数统一计算、缓存和复用，不为每个功能另做一套。新增消息或内容变化时更新计数；选择消息范围可利用累计计数，发送前再检查最终组装输入。分类器同样在请求前检查容量，但不能借此触发主 session 压缩或改写历史。

预算包含 system（含框架固定定义）、工具、当前有效历史、待交付消息、图片、宿主实际注入的其他辅助内容和末尾状态区，并留出输出和压缩指令的空间。辅助内容即使在插件选择消息范围之后才由宿主加入，也必须在最终组装检查中计入，不能当作免费空间；同一内容不重复计数。窗口大小、输出预留和宿主压缩配置以实际模型为准，不能写死为 1M 或固定 80 万 token。本地计量仍可能与服务端有差异，不能把文本分词结果当成完整请求的精确价格。

DeepSeek 的 tokenizer 文件和消息模板按兼容的模型系列复用，不按每个日期版本复制一套；以对应模型的官方实现为依据，不拿旧模型的 tokenizer 宣称新模型计数准确。切换计量规则时使旧计数缓存失效，不自行维护分词算法。兼容依据见[官方 tokenizer 文档](https://github.com/deepseek-ai/deepseek-recipe/blob/main/docs/tokenizer.md)。

普通交付按下面的顺序执行：

1. 确定本次处理范围，把待交付背景和本次触发消息暂存在插件中，先检查总大小。
2. 超过安全预算时，等待主会话空闲，通过宿主正式接口压缩已有历史。本次待交付消息不先塞进历史，也不交给这次 compact。
3. 压缩成功后，沿用现有规则同步 system，再按最新历史和状态重新计算空间。
4. 优先保留本次触发消息原文；默认从积压左侧移除较早的完整消息，保留装得下的最近部分。不截断工具调用与结果对。
5. 告知模型哪些消息范围没有提供，再把剩余背景和本次触发消息交给主模型，正常回复或沉默。compact 本身只生成摘要，不代替这次聊天请求。

没有可压缩内容时继续按剩余空间选择积压，不能反复调用无效 compact。压缩失败、输入预算本身不足或单条触发消息仍然超限时，保留原消息，记录并反馈原因；不静默 reset、截掉触发消息或无限重试。分类器输入过大时采用相同的默认左截断选择规则，并标明缺失范围；它不会因此推进主模型的处理位置。

左截断会遗漏尚未读取的内容，这是默认策略的明确取舍，不能继续承诺任意积压都会完整进入模型。性能验证测量首次载入、日常新增、超大积压和切换模型的开销，不预先承诺具体毫秒数。

### 第 3 批实际实现

- 插件数据目录的 `messages.sqlite` 保存群聊和私聊的完整源事件、准备后的正文、判断结果、投递记录和 OneBot 发送进度，不受 `chatLog` 控制。旧 `address-classifier/*.json` 校验后一次性迁入，旧文件保留；坏记录只阻止对应聊天，修复后重启重试。旧版已删除的正文无法补回，只迁移仍保留的去重 ID。
- `pending` 是尚未交付，`reserved` 是正在接纳，`admitted` 是已进宿主，`processed` 是模型正常结束，`failed` 是接纳后未正常完成，`omitted` 是因容量未提供。恢复时同时检查宿主持久 inbox、用户消息与所属轮次的结束事件；没有接纳证据才恢复待交付，无法核实的旧会话保守留作失败记录，不自动重跑工具。
- 历史查询统一使用 `qq_history`，旧群历史、私聊历史和 `qq_messages` 入口退出。SQLite 同时保存收到的消息与机器人发送记录，支持按时间分页、序号定位及长正文续读，单次最多 20 条，完整 JSON 最多 12000 字符（含元数据和转义），局部结果携带续读位置；处理和发送状态可选显示，未确认的回复不能当作已送达。默认查询当前获准聊天；跨聊天仅授权账号私聊可用，目标也须获准，与好感度无关。旧 Markdown 按聊天一次性导入，原文件保留，细节见[配置说明](configuration.md#语音聊天记录与空间工具)。回查不推进位置，不把旧内容当新用户证据。`/status`、`/cwd` 的处理计数不包含导入档案和机器人发送记录。
- 原始记录目前不自动删除；积压、未提供和失败记录的本地附件受保护。正常完成后的附件恢复原缓存规则（QQ 缓存文件超过 200 个时，每次清理至多 20 个不受保护的文件），因此历史原文可查不代表所有附件仍在。宿主保管的分类图片引用沿用宿主附件规则。清理数据库、旧迁移文件或受保护附件应在停用插件并备份后由管理员明确执行；没有后台悄悄清除原文的任务。
- 按完整回复保存每段外发计划。`queued` 尚未尝试，`sending` 已尝试但还没回执（重启后视为不确定），`sent` 已确认，`rejected` 是协议端明确拒绝，`not-sent` 是确定未调用（如请求前断线、限流或前段失败后停止），`uncertain` 是请求结果未知。正文与工具消息共用有效消息 ID 确认，负数和零值有效；缺少 ID 不冒充成功，也不推断确定没发。工具出口的发送也单独记账；没有自动重发或重跑整轮的行为。只提供状态查询和记录，重发操作入口尚未提供。
- 使用随包分发、有来源版本和校验和的 DeepSeek 官方 tokenizer；`contextTokenizerFamily` 选择 `v41` 或 `v4`，须与实际使用的模型系列匹配。同一系列的同一正文跨功能共用缓存，后台线程分词，SQLite 保存计数。文本用 tokenizer，图像和文件使用宿主实际模型的投影接口；另为消息结构留固定余量。这是本地预算，不是消息模板或服务端账单的精确复现。
- 窗口及输出预留来自宿主 `llm.prepareCall`；缺少声明就保留消息并报错，不猜 1M。交付预算使用宿主实际压缩比例和预留配置；主请求、工具续调及 compact 在 `llm/stream` 最终边界再次检查硬窗口，含宿主后来加入的内容。分类器只裁自己的输入，标明缺失并移除对应图片，不改主会话；记忆维护也复用计量，超限保留维护任务。
- 容量失败记录原因并通知一次；相同消息范围及配置不因每秒恢复检查而反复压缩。新消息、相关配置或会话变化后才再次尝试。已经接纳的失败范围不自动追加；沉默按正常完成记账。计分仍留待后续情绪功能，本批不实现分批摘要。

验证方法与覆盖范围见 [TESTING.md](../TESTING.md)。

## 5. 可选：分批摘要

默认关闭。开启后，装不下的较早积压按时间分批整理成摘要，最后把摘要、能保留的近期背景和本次触发消息原文一起交给主模型。每个摘要请求及最终请求都必须装得下；它会增加模型调用和延迟。

摘要过程不发送聊天、不执行工具，不直接写成长期记忆或情绪计分结果。保留来源范围和已完成进度，避免重启后反复摘要。失败时保留进度、明确报错，不偷偷改回左截断。摘要不能保证保留全部原文细节，原始记录仍用于回查。

### 实际行为

- 设置页“积压消息”提供 `backlogSummaryEnabled`，默认 `false`；`backlogSummaryTimeoutMs` 默认 `60000`，限制每批等待时间。群聊和私聊共用。关闭或原文全部装得下时，不调用摘要模型。
- 先通过宿主正式接口 compact 已有主历史，本次积压、触发消息及动态状态不参与这次压缩。仍超预算才摘要旧积压。最后的聊天请求包含“旧积压摘要 + 近期原文 + 本次触发原文”，摘要放在对应原文之前，不放入 system 或动态状态区；进入主历史后可随正常聊天历史参与以后的 compact。
- 摘要沿用主会话当前的 provider、model 和推理强度，独立请求且工具列表为空。采用滚动合并，每批带上一份摘要与下一批原文；摘要输出预留最多 4096 token，并受主模型输出上限和当前剩余空间约束。单条旧消息过长时按连续文本片段处理，记录消息序号、ID、时间及原文位置，不修改原文；本次触发消息必须完整保留，单条放不下直接停止。
- 所有请求复用统一计量和缓存，每批先累加原文片段的计数，发送前检查最终组装输入；摘要完成后重新读取主历史、末尾状态及其他辅助输入，再检查最终聊天请求。模型输出为空、超出摘要预留、异常结束或包含工具调用，均视为失败，不拿局部结果交付。
- SQLite 每批保存合并摘要、来源校验及原文位置，完成一批才推进。重启或换主 session 后，来源与摘要策略仍一致就继续；原文、待处理前缀、模型路由、分词系列或摘要大小要求变了，需要重新整理受影响范围。修改超时不使成功进度失效。远端已生成但本地尚未保存时崩溃，最后一批可能再次请求，不能承诺模型调用严格恰好一次。
- 卸载取消在途请求。每批前后及最终交付前重新检查聊天权限、当前 session、触发条件及相关配置；条件变化则停止旧交付，按当前条件重新安排，不把旧任务投到新会话。普通失败保留原文和成功进度，记录原因并反馈一次；同一范围不会无限重试，新消息、相关设置或会话变化后才再尝试。
- 摘要来源与近期原文在同一投递事务中接纳，恢复仍核对宿主证据；已接纳的范围不自动重放。来源单独记为 `summarized`，表示只提供了摘要，不能标成完整原文已读；`/status`、`/cwd` 显示“已提供摘要”。近期原文继续按普通消息记账，记忆维护的新增用户依据只列这些原文，不列摘要覆盖的旧来源。
- 原始 SQLite 记录与摘要覆盖的本地附件继续保留，历史查询按原权限回查。摘要只处理已有正文和附件引用，不额外看图，不声称理解附件内容，也不承诺远端链接一直有效。沉默、聊天发送结果和失败不重做工具的规则保持不变。

## 6. 实施与验收入口

批次状态、执行顺序和后续情绪开发统一见[当前进度与下一步](progress.md#当前进度与下一步)。历史上的第 1～4 批分别对应沉默与回复出口、群聊触发、消息保存与默认超窗处理、可选分批摘要。资料检索独立于消息交付，其行为见[参考资料](knowledge.md)。

每批只实现对应行为、设置迁移和必要测试。完整消息保存必须与容量检查一起使用，不能上线无限拼接。验证客观逻辑和必要性能，测试覆盖及真实环境限制见 [TESTING.md](../TESTING.md)；是否自然、是否值得接话由使用者实际反馈。
