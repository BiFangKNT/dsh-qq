# QQ 工具整理计划

状态：第 1 步已完成，第 2～4 步待实施。更新：2026-11-14。

当前定义了 19 个 QQ 工具，全部有对应实现。问题主要是文字发送入口重叠、部分工具在无法使用时仍注册，以及跨聊天发送的权限不完整。无需为了减少工具数量，把不同操作合成一个大工具。

本文记录已确认的整理范围与实施顺序。第 1 步已删除人设中的工具名检查、启动和重载警告，以及对应测试；其余设计尚未实施。

## 已确认的决定

已经确认：

- 已删除 `TOOL_TOKENS`、`personaLeaks()`、启动和重载时的两处人设警告，以及对应测试。它们原先只检查人设是否包含工具名，不负责注册或授权；用户可以在人设里描述工具使用偏好。
- `qq_memo` 最终由统一资料检索替代，不再长期保留一套共享记忆或通用共享写文件功能。
- 查梗与角色资料共用资料检索入口，由程序建立索引，不要求普通用户自行准备特定结构的 SQLite 数据库。该入口尚未实现。
- `qq_images` 历史取图继续不受实时成员图片屏蔽限制。不能借这次整理改变已确认的行为。
- 保留商城表情自动登记：收到可用的 `mface` 后保存重发所需的 ID、名称等信息，不调用模型决定是否登记，也不下载图片。自动登记不代表必须发送。
- 商城表情登记与普通图片收藏分开说明。`faceCollectHint` 只描述普通图片收藏，不控制商城表情登记；不能继续声称留空就“什么都不收藏”。
- 工具按功能分组：基础聊天能力默认提供，QQ 互动和表情包使用默认开启，合成语音和发布空间默认关闭，资料查询配置后提供。具体范围见下表；这些设置尚未实现。

- 跨聊天发送仅允许授权账号私聊发起，当前聊天和目标聊天均须在允许服务的范围内。
- 普通图片收藏：`faceCollectHint` 留空时不自动收藏，但用户明确要求时仍可收藏；填写规则后，允许模型按规则收藏。商城表情自动登记不受该字段影响。

本轮讨论的行为选择已确认，没有剩余待确认项。文字发送的合并、兼容和代码组织由实现者负责；实施中若出现现有决定无法覆盖的实际问题，再单独确认。尚未实现的设计不能写成当前已有行为。

## 现有工具与保留理由

下表完整列出 19 个工具。归为一行表示用途相关，不表示必须合并。

| 工具 | 当前用途 | 整理安排 |
| --- | --- | --- |
| `qq_memory` | 查询、修改当前事项、长期事实和已确认词义，查看版本 | 保留。自动记忆维护不能替代用户主动查询和更正 |
| `qq_history` | 查询聊天收发原文、翻页、续读长消息 | 保留。原文与记忆摘要不是同一份数据 |
| `qq_images` | 根据消息 ID 从协议端重新获取图片并缓存，返回本地路径 | 保留。文字历史查询不等于取回图片；远端链接失效时仍可能失败 |
| `qq_send`、`qq_reply` | 普通文字发送、引用发送；`qq_send` 还能指定其他聊天 | 合并为一个文字发送工具，引用作为可选参数 |
| `qq_send_image`、`qq_send_file` | 发送图片气泡、上传可下载文件 | 都保留。协议操作和接收者看到的结果不同 |
| `qq_recall` | 撤回消息，默认撤回最近发送的一条 | 保留。需要修正已发消息时有独立用途 |
| `qq_poke`、`qq_react`、`qq_like`、`qq_face` | 戳一戳、消息表态、名片点赞、发送内置表情 | 都有独立用途；随默认开启的 QQ 互动功能提供 |
| `qq_mface`、`qq_faces`、`qq_keep_face` | 发送表情包、查收藏、收藏本地图片 | 三者不重复；查找和发送由表情包使用开关控制，普通图片收藏按单独规则处理 |
| `qq_send_voice` | 用 Windows SAPI 合成并发送语音 | 保留为可选能力；当前实现只能在 Windows 使用 |
| `qq_qzone_send` | 发布 QQ 空间说说 | 保留为可选能力；保持授权账号私聊、确认后发布、限制尝试次数和不自动重发 |
| `qq_meme` | 查询特定 SQLite 梗词库 | 现有实现过渡保留，后续并入统一资料检索 |
| `qq_memo` | 读写配置的共享目录中的 Markdown 和文本文件 | 配置目录后才注册；过渡保留，后续由资料检索替代，旧文件保留 |

普通模型正文已经由插件自动发送，但文字发送工具仍可用于引用某条消息、处理过程中发送消息，以及经授权向其他聊天发送。不能因为存在自动发送就直接删除全部文字发送工具。

`read_image` 来自宿主预设，不是 QQ 插件定义的工具；`[SILENT]` 是控制外发的标记，也不是工具。删除人设检查不会删除这些能力。

代码入口：[主要工具](../src/tools.js)、[语音与空间](../src/tools-extra.js)、[记忆](../src/memory-tools.js)、[聊天原文](../src/message-tools.js)、[共享文件](../src/shared-files.js)。

## 工具开关与默认值（已确认，待实现）

当前除 `qq_memo` 按目录配置决定是否注册外，其余 18 个工具没有各自的启停开关，都会尝试注册。注册成功不代表本次请求一定提供，也不代表当前平台和协议端支持。下面是已确认的后续设计，不是当前已经存在的设置：

| 功能 | 确定的默认值 | 范围 |
| --- | --- | --- |
| 基础聊天能力 | 提供，不另设总开关 | 文字、引用、图片、文件、撤回、聊天记录、历史取图和统一记忆；继续检查原有聊天访问权限 |
| QQ 互动 | 开 | 戳一戳、消息表态、名片点赞、内置表情 |
| 表情包使用 | 开 | 查找和发送已有收藏；开启使用不代表允许自动收藏所有普通图片 |
| 合成语音 | 关 | 用户主动开启；当前 Windows SAPI 实现只在 Windows 提供，声音名称留空仍表示使用系统默认声音 |
| 发布空间 | 关 | 用户主动开启；授权账号私聊、确认和发布次数限制继续有效 |
| 资料查询 | 配置后提供 | 现有查梗、共享文件及后续统一资料检索；不提供注定只能返回“未配置”的入口 |

按功能分组，不给每个小工具单独增加开关。关闭某组时，不再向模型提供对应工具，执行端也检查，避免旧请求仍能绕过关闭操作；具体更新时机需核实宿主预设接口。

不增加独立的“商城表情自动登记”开关，保留现有收集行为。表情包使用开关控制模型能否查找、发送收藏，不因关闭使用删除已有收藏，也不把它当成普通图片收藏的总开关。普通图片的收藏方式按下一节已确认的规则处理。

## 图片缓存与表情收藏

这三件事用途不同，设置和说明必须分开：

| 行为 | 何时发生、保存什么 | 后续处理 |
| --- | --- | --- |
| 图片缓存 | 普通图片下载后供模型查看，属于聊天媒体文件 | 按既有附件保护和清理规则管理；不能因为查看过就自动变成长期收藏 |
| 普通图片收藏 | 模型调用 `qq_keep_face`，把本地图片复制到收藏目录并登记名称，供以后作为表情包发送 | 用户明确要求时可收藏；自动收藏仅在填写规则后由模型按规则执行，留空不自动收藏 |
| 商城表情自动登记 | 处理可用 `mface` 时，由程序把表情 ID、表情包 ID、key、名称等信息写入收藏清单 | 保留现有行为，不经过模型筛选、不下载图片、不受 `faceCollectHint` 限制；由发送工具决定是否使用 |

普通图片与商城表情共用现有收藏清单，不为这次说明另建一套收藏库。收藏清单不是聊天记忆，也不表示模型已查看图片内容。商城表情保存了 ID，不保证协议端以后一定能成功重发，仍以实际工具结果为准。

`faceCollectHint` 当前默认空，QQ 设置页没有入口，可通过运行端配置或插件 `settings.json` 设置。配置说明声称留空不收藏任何图片，实际提示词只要求“不主动收藏普通图片”，执行函数也没有对应的禁止检查；另有提示词错误地把 `qq_keep_face` 说成商城表情登记入口，后续应一并修正。

`faceCollectHint` 只描述普通图片自动收藏规则。后续补齐设置页入口，并统一设置、提示词和执行行为：留空不自动收藏，但用户明确要求仍可收藏；填写规则后允许模型按规则收藏。留空不是禁用收藏工具，不能用“规则为空就拒绝所有调用”实现。保留商城表情自动登记，不删除 `faceCollectHint` 或清空已有收藏。

发图的频率限制与收藏分开。当前 `qq_mface` 和 `qq_send_image` 共用默认至少间隔 90 秒、每小时最多 6 张的限制；登记新表情不会自动发送，也不会因此消耗发送额度。

## 需要解决的问题

### 1. 文字发送有两个相近入口

`qq_reply` 负责引用发送，`qq_send` 负责普通发送和指定目标。两者大部分参数处理、外发检查和协议调用相同。

保留一个文字发送工具，以可选的引用消息 ID 区分是否引用。普通回复仍直接输出正文，不要求每次调用工具。

跨聊天发送继续支持，按已确认的授权规则执行。旧工具的迁移和兼容方式由实现者确定；若保留旧入口作兼容，应限定迁移范围，不长期维护两份发送实现，也不再把两个等价入口同时推荐给新会话。

### 2. 无法使用的工具仍然注册

- `qq_meme` 无词库时仍注册，工具说明却声称有固定数量的现成词库；实际执行只能报告未配置。说明不符合部署事实。
- `qq_send_voice` 在非 Windows 上也注册，执行时才报告不支持 Windows SAPI。
- `qq_keep_face` 始终注册，配置和工具说明却把 `faceCollectHint` 留空描述为完全禁止收藏，无法准确表达“不自动收藏，但允许用户明确要求收藏”的规则。

按已确认的功能分组和实际运行条件判断可用性，不给每个工具新增一个开关。

普通图片的自动与手动收藏规则已经确认，详见上面的“图片缓存与表情收藏”。商城表情自动登记保留。

“已注册”和“本次请求提供给模型”是不同的事，宿主预设也会影响工具列表。调整前应核实宿主支持的筛选和更新方式；不能擅自修改宿主或重新设计预设系统。

### 3. 跨聊天发送缺少对应授权检查

`qq_history` 跨聊天查询已检查调用者和目标聊天权限。相比之下，`qq_send` 和 `qq_send_voice` 的 `to` 参数接受指定目标，执行路径没有对应的授权检查。

已确认的规则如下：

- 普通聊天只能向当前聊天发送。
- 向其他聊天发送仅限授权账号私聊发起，当前聊天和目标聊天均须获准。
- 校验在工具执行代码中完成，不能只写在提示词里。
- 权限失败时不合成语音、不调用外发接口，也不记录为已发送。
- 向其他聊天发送后，发送记录归目标聊天；不能把内容或消息 ID 记为当前聊天收到的回复。

这项修复可以独立于工具合并进行，不必等资料检索完成。

`qq_images`、`qq_react`、`qq_recall` 等接收消息 ID 的工具，也应核对目标消息的聊天归属及允许操作的对象。此处是后续检查项，不表示已经证实它们存在同一个漏洞；历史取图不受实时图片屏蔽限制，也不等于允许读取其他聊天的图片。

### 4. 工具调整还涉及发送记录和提示词

发送工具不能只完成协议调用。合并或限制工具时，还需检查：

- 成功、失败和回执不明是否正确记账；不能无条件声称发送成功。
- 工具发言与正常正文是否重复发送；图片、文件、表情与纯互动是否沿用各自的回复规则。
- 未知结果不通过重新执行整轮模型自动重发，避免再次执行工具。
- 工具说明、固定规则、设置描述、启动日志与测试是否仍使用已删除的名字。

这些是调整时必须验证的行为，不是要求本轮顺带重写所有外发代码。

## 分步推进

| 顺序 | 工作 | 状态与边界 |
| --- | --- | --- |
| 1 | 删除人设中的工具名检查 | 已完成；只删除检查、两处警告和专属测试，不改人设内容、工具或权限 |
| 2 | 修跨聊天发送权限、目标记账和无效工具说明 | 按已确认的授权规则实施；文字和语音一起检查，避免只修一条路径 |
| 3 | 合并文字发送入口，整理工具可用条件与收藏说明 | 合并和兼容细节由实现者负责，按已确认的分组默认值和普通图片收藏规则实施，保留商城表情自动登记 |
| 4 | 用统一资料检索替代旧查梗与共享文件入口 | 独立安排，沿用已有资料设计；不以本轮工具整理为由提前实现或删除旧数据 |

各步可以独立提交、检查和回退，不把四步捆绑成一次大改。用户决定的 `git add` 与提交边界保持不变。

## 验证标准

验证客观行为，不用“模型回复是否讨喜”作为通过标准：

- 删除人设检查后，包含工具名的人设能正常加载，启动和重载不再产生这类警告；现有提示词组装不变。
- 普通账号、授权账号、群聊和私聊的发送权限符合最终确认的规则；目标被禁用时不外发。
- 指定目标和引用消息同时出现时，不把其他聊天的消息 ID 当作当前目标的引用；校验失败无副作用。
- 当前聊天和跨聊天的文字、语音分别正确记账，沉默、失败和回执不明不冒充成功。
- 合并后普通发送与引用发送均可用，工具发言不与模型正文重复发送；旧入口按确认的迁移规则处理。
- 未配置资料库、不支持语音的平台、关闭收藏等情况下，工具说明与实际可用性一致；是否提供工具按最终设计断言。
- 商城表情自动登记不调用模型、不下载图片，按 ID 去重，不受普通图片收藏规则影响；登记本身不触发发送、不消耗发送额度。
- 普通图片缓存不因查看自动变成收藏；明确收藏后保存独立副本。已有商城表情和图片收藏不因升级或关闭使用而丢失。
- 普通图片收藏规则留空时，不产生自动收藏，但用户明确要求收藏仍能成功；规则非空时，模型收到准确的筛选规则，不能把它扩展为收到所有图片就收藏。商城表情登记不参与这项判断。
- `qq_images` 仍能按原设计回查图片，成员实时图片屏蔽不会扩展到历史取图。
- 新建、恢复会话及工具续调的工具列表符合预期，不重复注册，不误改普通 Agent 的能力。

先跑改动对应的专项测试，再跑全套和 mock 端到端测试。mock 只能证明模拟路径；真实 DSH 预设更新、协议端支持和实际 QQ 发送需另外验证，不以未实测的行为作完成依据。
